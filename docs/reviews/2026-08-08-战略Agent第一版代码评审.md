# 战略 Agent 第一版代码评审

评审日期：2026-08-08

评审对象：`D:\Code\Alavon_Agent` 当前工作树（包含尚未提交的战略 Harness 改动）

对照对象：

- `docs/design/10-战略认知与社会博弈.md`
- 其他领域、Harness、Coordinator 与安全设计文档
- 前身项目 `D:\Code\avalon-ai` 的对应实现

## 1. 结论摘要

当前版本已经显著改善前身项目中“只完成流程、不进行博弈”的结构性问题：Agent 能收到逐玩家构造的私有视图、自有记忆、公开事件增量、角色策略和多阶段讨论指令；公开发言与世界事实也已分层。前身 Prompt 中“优先返回最小合法 JSON”“Memory 默认省略”这类强烈诱导机械回答的设计已经移除。

但是，当前版本**尚不能通过信息差安全验收，也不能证明 Agent 已经具备稳定博弈能力**。本次评审确认了两个会改变游戏公平性的实际缺陷：

1. `SEE_PLAYERS_BY_CAMP` 和 `SEE_ALLIED_EVIL_PLAYERS` 会把其他玩家的 `exactRoleId` 交给 Agent。梅林因此直接知道谁是刺客、谁是莫甘娜，而不只是知道哪些玩家属于邪恶阵营。
2. `GameOrchestrator` 的顺序投票路径会公开每一张 `TEAM_VOTE_CAST`，后投票的 Agent 可以看到前面玩家的票型。

因此，对用户核心问题的准确回答是：

> 当前 Agent 不再必然退化为上一版那种“打卡总结 Agent”，而且没有发现读取其他 Agent 私有 Memory 的入口；但它仍存在角色信息越权和投票时序泄漏，足以破坏阿瓦隆的信息差。现有测试也没有验证真实模型是否会质疑、欺骗、修正信念或保持叙事一致性，所以现在不能宣称“Agent 已经足够聪明”或“核心游戏性已恢复”。

## 2. 主要发现

### [P0] 阵营可见性错误地泄露其他玩家的具体角色

证据：

- `avalon-core/.../RoleKnowledgeResolver.java:53-60`
- `avalon-core/.../RoleKnowledgeResolver.java:128-135`
- `avalon-app/src/main/resources/roles/merlin.yml`
- `avalon-app/src/main/resources/roles/assassin.yml`

`SEE_PLAYERS_BY_CAMP` 的语义应当是“知道这些玩家属于某阵营”，但实现同时写入：

```java
candidateRole.roleId(),
candidateRole.camp(),
List.of(candidateRole.roleId())
```

`SEE_ALLIED_EVIL_PLAYERS` 也做了相同处理。于是：

- 梅林不只知道 P2/P4 是邪恶，还知道 P2 是刺客、P4 是莫甘娜。
- 刺客、莫甘娜、莫德雷德会知道每个邪恶队友的精确角色，而不是仅知道邪恶同伴身份。
- Prompt 和审计中都能直接看到这些 `exactRoleId`，模型无需推理即可利用。

这违反 `03-游戏领域与规则扩展.md` 中 PlayerPrivateView “禁止包含其他玩家完整角色”的约束，也直接削弱派西维尔、莫甘娜伪装和刺客寻找梅林等核心博弈。

建议：

- `SEE_PLAYERS_BY_CAMP`：`exactRoleId=null`，只填 `camp`；候选角色应为空，或由规则显式给出候选集合。
- `SEE_ALLIED_EVIL_PLAYERS`：默认只暴露玩家身份和 `Camp.EVIL`，不要暴露精确角色。
- 只有 `SEE_PLAYERS_BY_ROLE` 才允许填写 `exactRoleId`。
- 增加按角色逐项断言的可见性矩阵测试，至少覆盖 Merlin、Percival、Morgana、Assassin、Mordred、Oberon。

### [P1] 顺序执行路径会让后投票 Agent 看到前票

证据：

- `avalon-runtime/.../GameOrchestrator.java:290-302`
- `avalon-runtime/.../PlayerObservationProjector.java:16-25`
- `avalon-runtime/.../RuntimePersistenceService.java:151`

`processVoteStep` 在每名玩家投票后立即追加：

```java
state.appendEvent("TEAM_VOTE_CAST", ..., Map.of("vote", voteAction.vote().name()));
```

观察投影只过滤 `ROLE_ASSIGNED` 和 `MISSION_ACTION_CAST`，因此 `TEAM_VOTE_CAST` 被当作 `WORLD_FACT` 发给下一个 Agent。持久化层也把该事件标为 `PUBLIC`。

Coordinator 批量路径做得正确：它冻结所有玩家上下文、并行收集投票，最后才写入 `TEAM_VOTES_REVEALED`。问题在于 `GameOrchestrator.step/runToEnd` 仍是可调用路径，两条路径的游戏语义不一致。

影响：

- 后投票 Agent 可以跟票或反向操纵，不再是同时秘密投票。
- Console、测试工具或未来绕过 Coordinator 的入口会得到不同的博弈结果。
- 黑名单投影无法阻止未来类似私有事件被默认公开。

建议：删除或封闭顺序投票路径，统一经 `GameCoordinator + ActionBatch`；如必须保留，`TEAM_VOTE_CAST` 必须是私有事件且所有 Agent 只观察最终 `TEAM_VOTES_REVEALED`。

### [P1] 信念更新的“证据约束”只存在于 Prompt，没有被宿主强制执行

证据：

- `avalon-agent/.../ValidationRetryPolicy.java:67-86`
- `avalon-core/.../PlayerMemoryState.java:103-105`

当前校验仅保证：

- 引用的 sequence 曾经对该玩家可见。
- 概率在 `[0, 1]` 范围内。

它没有保证：

- 信念发生显著变化时必须提供 Evidence Ref。
- Evidence Ref 与发生变化的玩家或结论有关。
- 同一玩家的角色假设满足互斥/归一化约束。
- `roleBeliefs` 包含合法玩家且不包含自己或不存在的玩家。
- 新输出不会无依据地整体覆盖旧信念。

模型可以把 P2 的邪恶概率从 0.1 改为 0.9，同时提交空 `evidenceReferences`，依然通过校验。这会让“看起来结构化的概率”替代真正推理。

建议实现基于前后差值的 Memory Policy：超过阈值的变化必须关联新可见证据；限制单次变化幅度；校验玩家集合；将每个信念与自己的证据列表绑定，而不是使用一个全局引用数组。

### [P1] 没有行为评测，无法证明真实 LLM 会博弈

当前仓库共有 9 个 JUnit 测试方法，覆盖 Prompt 关键字、非法 Evidence Ref、事件隔离、Memory 合并、讨论阶段、恢复和 Scripted 完整对局。它们没有调用真实 Provider，也没有测量：

- 是否质疑与公开证据冲突的发言。
- 是否会因新任务结果修正信念。
- 邪恶角色是否实施有收益且前后一致的欺骗。
- 梅林是否平衡引导好人和隐藏身份。
- 派西维尔是否保留 Merlin/Morgana 歧义。
- 刺客是否依据整局行为选择目标。
- 战略 Harness 是否优于最小 Prompt 基线。

因此，目前只能证明“宿主提供了更好的博弈条件”，不能证明“模型实际利用了这些条件”。这正是 `10-战略认知与社会博弈.md` 完成定义中尚未满足的一项。

建议先建立固定场景评测，再做完整对局评测。每个场景保存确定的公开时间线、私有身份和预期行为约束，至少对 3 个模型、20 个 seed 运行，并与前身 Prompt 或简化 Harness 做 A/B 对照。

### [P2] Memory 没有输入预算和压缩策略，长局可能再次退化

证据：

- `avalon-core/.../PlayerMemoryState.java:71-119`
- `avalon-agent/.../AgentTurnRequestFactory.java:85-87`
- `avalon-agent/.../PromptBuilder.java:72-78`

`worldFacts` 和 `publicClaims` 各限制为 300 条，但 `observations`、`commitments`、`inferredFacts`、`strategyState`、`communicationPlan` 没有大小或 Token 限制；每回合会把完整 Memory 重新放入 Prompt。设计文档给出了 16,000 Token 输入预算，代码中没有对应预算器、裁剪器或摘要压缩器。

影响是长局 Prompt 越来越长，模型更容易遗漏早期承诺、输出被截断或只做机械摘要。对 Anthropic 配置了输出上限，但这不是输入上下文预算。

建议引入确定性的 Memory Compactor：权威事件保留结构化索引，承诺和 Cover Story 去重，旧解释性文本按轮摘要，并在调用前记录实际 Token 预算与截断原因。

### [P2] 私有事件隔离使用黑名单，新增事件默认公开

证据：

- `PlayerObservationProjector.PRIVATE_TYPES`
- `DefaultDisclosurePolicy.PRIVATE_EVENT_TYPES`
- `RuntimePersistenceService.visibility`

三个位置分别维护事件可见性，而且默认行为都是公开。这次新增 `TEAM_VOTE_CAST` 就已经证明该模型容易失守。

建议把可见性作为 `GameEvent` 的强类型字段或事件定义元数据，并采用公开白名单/显式投影。Agent Observation、HTTP Event、SSE、Replay 应复用同一投影策略，避免三套名单漂移。

### [P2] 角色策略有差异，但 Agent 个体差异默认未落地

`RoleStrategyPlanner` 为七类角色提供了目标、约束、决策问题和允许的欺骗意图，这是有效改进。但 `cognition`、`communication`、`deception` 只是可选 Map，默认创建流程没有为不同 Agent 提供稳定参数。相同角色、相同模型、相同上下文的 Agent 仍会高度同质化。

建议提供版本化的 Agent Profile，并把风险偏好、证据阈值、领导倾向、质疑倾向和欺骗风格映射到明确字段及校验范围。评测时应区分“角色差异”和“人格差异”。

### [P2] 规范中的战略工具、确定性矛盾检测和两阶段推理尚未实现

当前每个动作仍是一次 Prompt 到一次结构化回复：

- 没有 `query_public_timeline`、`compare_vote_history`、`detect_public_contradictions` 等工具。
- 矛盾识别完全依赖模型文本推理。
- 没有根据不确定性或事件量触发“先更新信念、再决定动作”的两阶段执行。

这不会让当前版本必然失败，但会限制长时间线、复杂矛盾和刺杀决策的可靠性。它们应列为 P2 能力增强，不应包装成已经完成的 Harness 能力。

## 4. 与前身项目的关键差异

前身项目的 Prompt 明确要求“优先返回最小合法 JSON”，并允许 `auditReason` 和 `memoryUpdate` 默认省略；示例发言也高度模板化。这会把模型锚定为完成表单和汇报进度。

当前版本的改进包括：

- `memoryUpdate` 变为必填。
- Prompt 明确区分事实、主张和私有信念。
- 明确允许角色范围内的隐瞒和欺骗。
- 强制输出角色信念、策略状态、沟通计划、Cover Story 和 Evidence Ref。
- 讨论不再是每人一句后立即组队。

因此，当前版本的智能上限确实比前身高。但“字段更多”不自动等于“推理更深”。如果没有信念变化约束和行为评测，模型仍可能生成形式完整、内容空泛的战略 JSON。

## 6. 验证状态

本轮静态确认了 9 个 JUnit 测试方法。测试覆盖了部分关键结构，但缺少以下回归用例：

- `SEE_PLAYERS_BY_CAMP` 不得产生 `exactRoleId`。
- `SEE_ALLIED_EVIL_PLAYERS` 不得产生 `exactRoleId`。
- 任意投票者的上下文在揭票前看不到其他票型。
- 新增未知事件不能默认进入 Agent/Public/SSE 投影。
- 无证据的大幅信念变化必须失败。
- Memory 达到预算后仍能保留关键承诺和时间线。

本机当前终端没有可用的 `java`、`mvn` 或 Maven Wrapper，因此本轮无法实际执行测试。不能沿用或复述其他报告中“测试全部通过”的结论作为本轮已验证事实。

## 7. 修复优先级

### 第一批：恢复正确的信息差

1. 修复 `RoleKnowledgeResolver`，严格区分“看见阵营”“看见同伴”“看见精确角色”“看见候选角色”。
2. 统一所有正式推进路径到 Coordinator；投票和任务选择必须基于同一冻结状态批量收集。
3. 将事件可见性改为显式强类型策略，移除分散黑名单。
4. 为角色知识和投票不可见性增加回归测试。

### 第二批：防止结构化伪智能

1. 实现 Belief Delta + Evidence 绑定和变化阈值。
2. 校验角色信念的玩家集合、互斥关系和概率约束。
3. 实现 Cover Story/公开承诺冲突检测。
4. 实现 Memory Token Budget、去重、摘要和截断审计。

### 第三批：证明博弈质量

1. 建立 `docs/10` 中的 10 类固定场景评测。
2. 运行至少 3 个模型、20 个 seed，并按角色分层统计。
3. 与前身最小 Prompt 或关闭战略 Harness 的基线做 A/B。
4. 记录证据引用率、信念修正合理率、矛盾识别率、回应命中率、叙事冲突率、私有信息泄漏率和非法动作率。

## 8. 最终判定

- **是否仍是上一版同一种“完全没有博弈”的实现？** 否。观察、记忆、角色策略和讨论协议已发生实质变化。
- **是否还可能表现成空泛的进度总结 Agent？** 会。宿主减少了这种倾向，但尚无行为评测，且信念约束与输入预算不足。
- **是否还能访问其他 Agent 的私有 Memory？** 正式上下文中未发现该入口。
- **是否仍有破坏信息差的泄漏？** 有，而且是阻断发布的问题：精确角色泄漏和顺序票型泄漏。
- **是否可以宣称第一版成功解决了核心问题？** 现在不可以。应先修复 P0/P1，并用真实模型评测证明行为质量。
