# 战略 Agent 博弈能力综合评审报告

评审日期：2026-08-10  
评审基线：当前分支 `f09e974`  
综合来源：当前代码复核、`2026-08-08-战略Agent第一版代码评审.md`、`2026-08-10-战略Agent当前版本博弈能力评审.md`，以及外部 Agent 提供的静态评审意见。  
评审目标：判断当前 Agent 是否仍会退化为“按流程打卡、无条件相信、不会博弈和欺骗”的玩家。

## 1. 最终结论

当前版本已经基本消除了前身最致命的**信息差破坏问题**，但尚未证明、也尚不能由 Harness 保证 Agent 具备稳定的社会博弈能力。

更准确地说，项目已经完成了以下转变：

```text
前身：信息边界不可信 + 交互流程机械 + 没有战略闭环
当前：信息边界基本可信 + 具备战略交互接口 + 战略质量仍主要依赖模型自觉
目标：信息边界可信 + 宿主认知闭环 + 真实对局证明行为有效
```

因此当前项目可以定义为：

> **信息差安全基本达标、战略 Harness 骨架已落地，但战略执行约束和真实行为验收尚未完成。**

它已经不再是前身那种因为共享私有信息而从根本上无法博弈的系统；但仍然可能产出固定话术、无效信念更新、不回应具体证据、不切割邪恶队友、不维护欺骗叙事的“流程型 Agent”。

## 4. 已确认做对的部分

### 4.1 Agent 不再读取全局 Memory

`TurnContextBuilder` 从 `state.memoryOf(player.playerId())` 构造当前玩家的 `PlayerMemoryState`，`AgentTurnRequestFactory` 只投影该 Memory。正式请求中未发现 `memoryByPlayerId` 整体或其他玩家 `strategyState`、`communicationPlan`、Provider 原始响应的入口。

这解决了前身最致命的问题：Agent 的私有认知空间目前由 `gameId + playerId + agentInstanceId` 隔离，而不是共享一个全局对话历史。

证据：

- `avalon-runtime/src/main/java/com/example/avalon/runtime/service/TurnContextBuilder.java:42-78`
- `avalon-agent/src/main/java/com/example/avalon/agent/service/AgentTurnRequestFactory.java:42-50,87-89`
- `avalon-agent/src/main/java/com/example/avalon/agent/service/MemoryContextProjector.java:27-63`

### 4.2 角色知识不再无条件泄漏精确身份

角色知识解析已经区分 `exactRoleId`、`camp` 和 `candidateRoleIds`。Merlin 获取允许看到的邪恶阵营玩家而不是具体邪恶角色；Percival 的 Merlin/Morgana 候选不携带真实阵营；邪恶同伴知识也不会默认暴露具体角色。

这保住了 Avalon 的核心信息差。

### 4.3 秘密动作采用冻结批次

Coordinator 和直接 Orchestrator 路径都会先从同一个状态版本构造所有参与者 Context，再调用 Controller，最后统一提交。投票和任务动作不会按生成顺序进入下一位 Agent 的观察空间。

证据：

- `avalon-runtime/src/main/java/com/example/avalon/runtime/coordination/DefaultGameCoordinator.java:91-113`
- `avalon-runtime/src/main/java/com/example/avalon/runtime/orchestrator/GameOrchestrator.java:290-315`

### 4.4 讨论协议已经具备社会互动接口

当前运行时支持 Opening、Challenge、Targeted Response 和 Leader Synthesis，并验证 Challenge 必须点名、Response 必须引用对应质疑事件。它已经不是前身“所有人各说一句就结束”的纯独白流程。

这只是必要条件，不是智能证明；后续问题在于调度和内容质量仍缺少约束。

## 5. 阻断战略能力验收的问题

### P1：战略字段只要求存在，没有被宿主语义执行

`ValidationRetryPolicy` 当前主要验证：

- `memoryUpdate` 存在；
- Evidence Sequence 对当前 Agent 可见；
- belief 目标玩家存在；
- 概率在 `[0,1]`；
- 单次变化幅度受限；
- 已知阵营不能被 belief 反转。

它没有验证：

- `strategyState.mode/objective` 是否存在且适用于当前局势；
- `unresolvedQuestions` 是否来自真实争议；
- `communicationPlan.publicMessage` 是否等于最终公开发言；
- `evidenceToMention` 是否真的出现在发言或支撑动作；
- `deceptionIntent` 是否为当前角色允许；
- `coverStory` 是否与过去叙事一致；
- 信念变化方向是否符合证据语义。

`PlayerMemoryState.merge()` 随后会直接接受非空 Map。因此当前 Harness 强制的是“结构化战略字段”，不是“战略行为”。模型可以重复输出模板 Map 并合法完成对局。

证据：

- `avalon-agent/src/main/java/com/example/avalon/agent/service/ValidationRetryPolicy.java:71-134`
- `avalon-core/src/main/java/com/example/avalon/core/player/memory/PlayerMemoryState.java:74-110`

### P1：公开承诺没有由宿主确定性维护

设计要求宿主确定性记录玩家的公开承诺，但当前 `recordAction()` 只写入公开事件，Memory 中的 commitments 仍完全来自模型返回的 `commitmentsToAdd`。

这会产生三个后果：

1. 模型漏填时，公开说过的话不会进入承诺状态。
2. 模型可以把普通发言错误标记成承诺，或省略不利承诺。
3. Cover Story 一致性检查没有可靠的权威输入。

宿主至少应从结构化 Speech Act/Claim 中记录明确的投票意图、条件承诺、支持/反对关系和立场修正；模型可以解释承诺，但不能决定公开说过的话是否存在。

证据：

- `avalon-runtime/src/main/java/com/example/avalon/runtime/orchestrator/GameOrchestrator.java:384-446`
- `avalon-agent/src/main/java/com/example/avalon/agent/model/MemoryUpdate.java:49-54`

### P1：欺骗能力仍是 Prompt 级约定

`RoleStrategyPlanner` 为角色返回 `permittedDeceptionIntents`，但这只是 Prompt 输入。宿主没有拒绝不允许的 intent，也没有强制 Merlin 维护 `exposureRisk`，没有验证邪恶角色是否泄漏同伴知识，亦没有判断 Cover Story 是否与公开历史冲突。

因此当前可能出现两种相反错误：

- 邪恶 Agent 永远选择 `NONE`，完全不会伪装和误导；
- 好人或不允许某种欺骗的角色提交非法 intent，系统仍接受并计入战略指标。

证据：

- `avalon-agent/src/main/java/com/example/avalon/agent/strategy/RoleStrategyPlanner.java:15-29,56-64`
- `avalon-agent/src/main/java/com/example/avalon/agent/service/ValidationRetryPolicy.java:71-104`

### P1：现有评估器无法证明真实博弈，且没有进入产品验收链路

`StrategicBehaviorEvaluator` 位于 `avalon-testkit`。生产主链路没有调用它，也没有将 `meetsStrategicGate()` 结果记录为对局质量状态。

现有门槛可以被低质量输出刷过：

- 只需一次数值变化即可计作 belief revision；
- Evidence Ref 非空即视为 grounded，不检查方向；
- 非 `NONE` intent 或非空 coverStory 即计作 deception plan；
- 没有旧 Cover Story 时 narrative consistency 直接记为 `1.0`；
- Challenge/Response 只检查点名和事件引用，不检查是否回答问题。

这套指标适合作为结构烟雾报警器，不适合作为“Agent 已经聪明”的发布门槛。

证据：

- `avalon-testkit/src/main/java/com/example/avalon/testkit/StrategicBehaviorEvaluator.java:15-82`
- `avalon-testkit/src/main/java/com/example/avalon/testkit/StrategicBehaviorReport.java:16-33`

### P1：当前没有可复核的真实 LLM 行为证据

仓库内五个模型 Profile 均为 `enabled: false`，当前没有多模型、多 seed、角色轮换、同模型基线对照的对局报告。因此无法确认：

- Agent 是否抗从众；
- 新证据是否让信念向正确方向变化；
- Merlin 是否能引导但隐藏信息优势；
- Morgana 是否能建立可信的假 Merlin 叙事；
- 邪恶是否会切割而非机械抱团；
- Assassin 是否能利用全局历史识别 Merlin；
- 同角色不同 Agent 是否表现出稳定差异。

这是验收阻断项，不等同于代码缺陷。

## 6. 高影响实现问题

### P1：noop 基线无法正确将任务失败归因到任务成员

`NoopAgentGateway` 只处理 `MISSION_FAILED`，并从当前公共快照的 `currentTeamPlayerIds` 获取要提高怀疑值的玩家。但 `resolveMission()` 在写入结果事件后会清空提案和任务队伍；下一轮 Agent 处理 `MISSION_FAILED` 时，当前队伍通常已经为空。

因此 noop 基线很可能长期维持未知玩家 `0.4` 的固定先验，无法形成“组队 -> 投票 -> 任务结果 -> 信念变化”的基本闭环。

该问题不会直接限制真实 LLM，因为真实模型还能读取 Observation Delta 中的 `TEAM_PROPOSED` 和任务结果；但它会使离线演示、基线对照和无 Provider 场景继续呈现机械行为，从而使评测基线本身失真。

证据：

- `avalon-agent/src/main/java/com/example/avalon/agent/gateway/NoopAgentGateway.java:37-70`
- `avalon-runtime/src/main/java/com/example/avalon/runtime/orchestrator/GameOrchestrator.java:318-345`

### 关于“默认路径就是 noop”的精确结论

当前实际行为是：

- API 玩家未指定 `controllerType` 时默认为 `SCRIPTED`；
- 控制台新建游戏默认选择 `random` 模型池；
- 当前没有启用模型时，`random` 会在建局时明确失败，不会静默转 noop；
- 显式选择控制台 `noop` 时使用 `NoopAgentGateway`；
- 创建 LLM 席位但不给模型选择/provider 时，也会因 provider 为空进入 noop；
- 选择有效模型 Profile 后，Provider 失败会导致对局暂停，不会自动改用 noop。

所以问题不是“所有默认运行都偷偷使用 noop”，而是“仓库开箱状态无法完成真实 LLM 对局，且显式离线 LLM 路径仍然是机械基线”。

证据：

- `avalon-api/src/main/java/com/example/avalon/api/service/PersistentGameApplicationService.java:251-277,301-375`
- `avalon-app/src/main/java/com/example/avalon/app/console/AvalonConsoleRunner.java:224-305`
- `avalon-agent/src/main/java/com/example/avalon/agent/gateway/RoutingAgentGateway.java:23-29`

## 7. 其他重要缺口

### P2：讨论调度有固定仪式化倾向

每轮讨论固定执行所有 Opening、两个 Challenge、对应 Response 和 Leader Summary。宿主没有根据矛盾权重、不确定性、争议集中度或信息增益决定是否质疑以及质疑谁。

这让系统具备互动外形，但仍可能每局复现相同节奏和话术。特别是 noop 的 Response 固定为“我的判断只基于公开信息”，并没有回答被问的具体内容。

### P2：设计中的战略工具尚未落地

未发现以下工具的正式实现：

- `get_claim_history`
- `get_vote_history`
- `detect_public_contradictions`
- `compare_team_outcomes`
- `evaluate_team_combinations`
- `get_my_public_commitments`

真实模型可以从原始事件自行推理，但把所有历史关联都交给模型会消耗上下文，并增加漏证据、顺序混淆和模板化判断的概率。Harness 应确定性整理事实，模型负责解释，而不是每轮从 JSON 历史重新做数据工程。

### P2：私有知识表达校验存在不确定词绕过

`PrivateKnowledgeExpressionValidator` 只要发现一个子句含“可能、怀疑、倾向”等词，就跳过整个子句的确定性断言检查。例如“可能 P2 是梅林，但 P3 就是刺客”可能利用前半句的不确定词绕过后半句检查。

该问题不会让 Agent 读取到原本不可见的数据，但可能让 Agent 把规则允许的私有精确信息或歧义候选以不受控方式公开表达。

### P2：Agent 差异化配置默认不足

`PlayerAgentConfig` 已有 cognition、communication 和 deception 参数，控制台也会提供一套默认 Map；但同一预设下所有席位得到相同参数，模型 Profile 也只描述连接和生成参数。当前没有可命名、可版本化、可对照的不同人格 Profile。

角色差异不等于 Agent 差异。即使角色策略不同，同角色 Agent 仍可能表现得几乎一致。

### P2：Belief 模型过度简化

当前 `roleBeliefs` 实际表示“邪恶阵营概率”，没有实现设计中的完整角色概率分布、支持/反对证据、置信等级和结构化 contradiction。它足以支持基础怀疑排序，但不足以表达 Percival 的 Merlin/Morgana 区分、Assassin 的 Merlin/Percival 候选排序和多角色互斥约束。

## 8. 为什么当前仍可能出现“无脑信任”

Prompt 已明确告诉模型 `PUBLIC_CLAIM` 不等于事实，但 Harness 没有确定性测量模型是否真的遵守。当前系统只会拒绝越界 Evidence ID 和过大的概率跳变，不会拒绝以下行为：

- 多数人重复一个无证据主张后，Agent 小幅、连续地跟随调整 belief；
- Agent 引用一个与结论无关但包含目标玩家 ID 的事件；
- Agent 每轮都说“继续观察”，但填一个合法 strategyState；
- Agent 回应质疑时只引用质疑事件，不回答问题；
- 邪恶角色永远不欺骗，只输出 `NONE`；
- 模型用同一套固定发言完成所有角色的 Opening。

所以当前能保证“不会一步从 0.1 无证据跳到 0.9”，不能保证“不会通过多次小步无脑从众到 0.9”。

## 9. 整改优先级

### 第一阶段：让战略字段成为宿主契约

1. 为 `strategyState`、`communicationPlan` 和 `deceptionIntent` 建立按阶段裁剪的强类型 Schema。
2. 宿主校验角色允许的 deception intent、Merlin exposureRisk 和 Cover Story 变更理由。
3. 校验 communication plan、最终 Speech Act、公开文本和动作的一致性。
4. 从已接受的公开发言确定性记录承诺、立场和修正，不依赖模型主动添加。
5. 将 Evidence 关联从“包含玩家 ID”提升到事件类型、队伍成员和结论方向的语义规则。

### 第二阶段：让 Harness 提供可计算的社会证据

1. 实现 claim、vote、team outcome 和 commitment 历史查询。
2. 实现确定性候选矛盾检测，但不自动判定阵营。
3. 任务结果事件或关联记录应能直接追溯当轮任务队伍。
4. 根据矛盾、不确定性和信息增益动态选择 Challenge，而不是固定两个质疑席位。
5. 为 Percival、Assassin 等角色维护多角色候选，而不只是一维邪恶概率。

### 第三阶段：建立真实行为验收

至少建立以下固定场景：

1. 发言与投票冲突时识别矛盾，但不直接定罪。
2. 多数人无证据结论下保持独立判断。
3. 新任务结果推翻旧假设时正确修正。
4. Merlin 使用公开证据包装正确引导。
5. Morgana 混合正确判断和误导并维持叙事。
6. 邪恶在合适情境下切割队友。
7. Assassin 利用历史准确度和引导行为选择目标。
8. 被点名后回答具体问题，而不是输出通用防御句。
9. 违反公开承诺时说明新证据和修正原因。
10. 信息不足时维持不确定性。

同一模型应比较战略 Harness 与简化基线，进行座位轮换和角色轮换，至少运行 20 至 30 个 seed，并报告：

- Evidence 引用有效率和语义相关率；
- belief 变化方向正确率；
- 通用发言重复率；
- 具体问题回应率；
- 角色行为可区分度；
- 欺骗合法率、叙事一致率和受众影响；
- 阵营胜率及置信区间；
- 首次合法动作率、延迟和 Token 成本。

## 10. 最终回答

### Agent 是否还会读取其他 Agent 私有信息？

当前正式代码路径中没有发现该入口。精确角色、跨玩家 Memory 和顺序秘密票这三个前身级致命问题可以判定为**代码级基本解决**。

### Agent 是否还会像上一版一样完全没有博弈？

仍有可能，但原因已经不同：不再是“信息全开导致无博弈”，而是“战略字段缺少宿主语义约束、承诺和矛盾没有确定性闭环、默认离线基线机械、真实模型没有经过行为验收”。

### 当前能否宣称新版成功？

不能。当前可以宣称的是：

> 新版已经建立了正确的信息隔离和战略交互基础，显著提高了模型进行博弈的上限。

当前还不能宣称的是：

> Agent 已经稳定学会欺骗、抗从众、证据推理、邪恶切割、Merlin 伪装和 Assassin 识别。

这些能力必须通过宿主契约完善和真实 Provider 的多场景、多 seed 对照实验共同证明。

本报告只进行了静态代码审查和两份评审结论的交叉复核，没有修改业务代码，没有运行自动化测试，也没有运行真实 Provider 对局。
