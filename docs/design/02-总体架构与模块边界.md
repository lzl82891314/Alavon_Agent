# 02 - 总体架构与模块边界

## 1. 架构风格

项目采用六边形架构思想下的 Spring Boot 模块化单体：

- 单进程降低学习、调试和运行成本。
- Maven 模块和 Java 包边界保证职责隔离。
- 核心通过端口接口依赖外部能力。
- Console、Web、数据库和模型 Provider 都是适配器。
- 当某个模块未来需要独立部署时，已有端口可以转为远程协议。

第一版不采用微服务。当前问题的核心是边界和运行时设计，不是网络拓扑。

## 4. 模块职责

### 4.1 `avalon-domain`

纯 Java 领域内核，负责：

- 游戏聚合、状态和值对象
- 领域命令和领域事件
- 合法动作的领域类型
- 规则引擎端口
- 玩家控制器端口
- 私有视图和公共视图模型
- 不变量和领域异常

禁止依赖：

- Spring
- Jackson
- 数据库
- HTTP
- Provider SDK
- Spring AI

### 4.2 `avalon-rules`

负责可版本化规则资产：

- Rule Pack 加载
- 角色定义
- 开局模板
- 阶段定义
- 可见性规则
- 胜负规则
- 配置引用与一致性校验
- 复杂规则的 Java 扩展实现

它依赖 `avalon-domain`，不得依赖 Harness 或交付层。

### 4.3 `avalon-model-spi`

定义厂商无关的模型协议：

- `ModelClient`
- `ModelRequest`
- `ModelResponse`
- Typed Content Items
- Tool Definition / Tool Call / Tool Result
- Structured Output 定义
- 流式事件
- 使用量和错误分类
- Provider 能力描述

该模块不包含游戏类型，使其可以单独演进。

### 4.4 `avalon-harness`

负责 Agent 的受控执行：

- Agent Profile 解析
- Context Assembly
- Skill Resolution
- Tool Policy
- Memory Policy
- Observation Delta 与逐玩家观察游标
- Belief State、Strategy State 和角色策略
- Public Commitment、Cover Story 与受控欺骗
- Model Routing
- 输出解析与 Schema 校验
- 领域预校验
- 重试、修复、暂停和降级
- Agent Trace 与审计摘要

它依赖 `avalon-domain` 和 `avalon-model-spi`。

### 4.5 `avalon-application`

应用用例与事务边界：

- 创建、开始、推进、暂停、恢复、结束游戏
- 根据 NextRequirement 创建并推进 Action Batch
- 对多人动作实施逻辑并行和披露隔离
- 调用 Player Controller
- 提交 LLM、Human 或 Scripted 动作
- 保存事件和快照
- 发布应用事件
- 查询公共、私有和管理员视图

应用层协调领域和 Harness，但不实现具体规则或 Provider 协议。

### 4.6 `avalon-provider-openai`

原生 OpenAI Responses API 适配器：

- HTTP/SSE 协议映射
- Responses typed Items
- Structured Outputs
- Function Calling
- `previous_response_id` 可选支持
- OpenAI 错误、限流与使用量映射

它只能实现 `avalon-model-spi`，不得引用游戏聚合。

### 4.7 `avalon-provider-spring-ai`

可选对照实现：

- 将 `ModelRequest` 映射到 Spring AI ChatClient/Model API
- 将 Tool Definition 映射到 ToolCallback
- 接入 Spring AI Advisor 和 Observability
- 把框架异常映射为统一 `ModelFailure`

该模块用于学习和比较，不成为领域层的必需依赖。

### 4.8 `avalon-persistence`

负责：

- Game Event Store
- Game Snapshot Store
- Action Batch / Submission Store
- Agent Memory Store
- Agent Trace / Audit Store
- 配置冻结快照
- Flyway Migration
- Spring JDBC（默认）与可选 JPA 只读投影实现

实体类不得向上层泄漏。通过 mapper 转换为领域或应用 DTO。

### 4.9 `avalon-delivery-console`

负责终端交互：

- 命令解析
- 表格和时间线输出
- 真人动作输入
- 流式事件展示
- 调用 Application API

Console 不读取 Repository，也不直接调用规则引擎。

### 4.10 `avalon-delivery-web`

负责：

- REST Commands
- REST Queries
- SSE Event Streams
- 鉴权后的私有视图
- 错误响应映射
- 未来 GUI 的稳定后端接口

### 4.11 `avalon-bootstrap`

唯一 Spring Boot 启动模块：

- 自动装配所有适配器
- 读取配置
- 注册 Provider、Rule Pack、Skill 与 Controller
- 选择 Console、Server 或 Combined 启动模式
- 启动时执行完整配置校验

## 5. 依赖规则

允许的核心依赖方向：

```text
rules -> domain
model-spi -> no game dependency
harness -> domain + model-spi
application -> domain + harness
providers -> model-spi
persistence -> application ports + domain
delivery -> application
bootstrap -> all concrete modules
```

禁止的依赖：

- `domain -> application`
- `domain -> harness`
- `domain -> persistence`
- `harness -> provider-openai`
- `provider-openai -> domain`
- `console -> persistence`
- `web -> provider-openai`

## 6. 核心端口

```java
public interface PlayerController {
    PlayerDecision decide(PlayerTurnContext context);
}

public interface GameRuleEngine {
    DecisionResult decide(GameState state, GameCommand command);
}

public interface GameCoordinator {
    AdvanceResult advance(AdvanceGameCommand command);
    SubmitActionResult submit(SubmitPlayerActionCommand command);
}

public interface ActionCollector {
    ActionBatch open(NextRequirement requirement, TurnToken turnToken);
    SubmissionResult submit(ActionSubmission submission);
    Optional<CompletedActionBatch> completed(ActionBatchId batchId);
}

public interface AgentHarness {
    AgentExecutionResult execute(AgentExecutionRequest request);
}

public interface ModelClient {
    ModelResponse execute(ModelRequest request);
    Flow.Publisher<ModelStreamEvent> stream(ModelRequest request);
}

public interface GameEventStore {
    List<GameEvent> load(String gameId, long afterSequence);
    void append(String gameId, long expectedVersion, List<GameEvent> events);
}

public interface GameSnapshotStore {
    Optional<GameSnapshot> loadLatest(String gameId);

```

GameCoordinator、NextRequirement 和 Action Batch 的完整规范见 [GameCoordinator 与动作收集规范](12-GameCoordinator与动作收集.md)。

接口名称可以在实现阶段微调，但职责与依赖方向必须保持。

## 7. Spring 的使用边界

Spring 适合负责：

- Bean 装配
- Configuration Properties
- 事务
- Web 和 SSE
- 数据访问
- Metrics 与 Health
- 生命周期管理

Spring 不应负责表达：

- 游戏阶段和胜负逻辑
- 玩家可见性真相
- Agent 的核心状态机
- Provider 无关的模型协议

领域对象不使用 `@Component`、`@Service` 或 JPA 注解。

## 8. 注册表而非巨大条件分支

可扩展类型通过注册表解析：

```java
public interface NamedComponent {
    String id();
}

public final class ComponentRegistry<T extends NamedComponent> {
    private final Map<String, T> components;

    public T require(String id) {
        T component = components.get(id);
        if (component == null) {
            throw new IllegalArgumentException("Unknown component: " + id);
        }
        return component;
    }
}
```

适用对象包括：

- Rule Pack
- Phase Handler
- Victory Condition
- Player Controller Factory
- Provider Adapter
- Skill
- Tool
- Memory Policy
- Harness Profile

## 9. 同步与异步边界

单个领域决策保持同步和确定性。模型调用可能耗时，因此应用层将“请求玩家动作”和“提交玩家动作”设计为两个概念：

```text
Game needs action
-> create TurnRequest
-> controller starts work
-> receive ProposedAction
-> submit command to domain
```

V1 可以在 Console 自动运行时同步等待 LLM，但持久化状态必须能表达 `WAITING_FOR_CONTROLLER`，避免未来异步化时重构领域模型。

## 10. 启动模式

支持三种模式：

| 模式 | 行为 |
| --- | --- |
| `console` | 启动交互式 Console，可选关闭 Web Server |
| `server` | 启动 REST/SSE，不启动交互式命令循环 |
| `combined` | 同时启动 Console 和 Web，适合本地观察 |

默认模式为 `console`。所有模式共享同一 Application Service 和持久化实现。

## 11. 为未来拆分保留的边界

如果未来需要独立模型网关或分布式 Worker，可以把以下端口转换为消息或 HTTP，而不改变领域层：

- `ModelClient`
- `PlayerController`
- `GameEventPublisher`
- `HumanActionInbox`

在出现真实的吞吐、隔离或部署需求前，不提前引入分布式事务、消息中间件或服务发现。
