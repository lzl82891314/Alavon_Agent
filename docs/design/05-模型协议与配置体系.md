# 05 - 模型协议与配置体系

## 1. 设计结论

项目默认原生支持 OpenAI Responses API，但业务和 Harness 不依赖 OpenAI 类型。

当前实现中，模型档案必须通过顶层 `protocol` 明确声明协议。`provider` 只标识实际服务商，`protocol` 标识 HTTP/API 语义，`modelName` 是上游模型 ID；三者不能互相推断。`OPENAI_RESPONSES` 请求 `/v1/responses`，`OPENAI_COMPATIBLE_CHAT` 请求 `/v1/chat/completions`，`ANTHROPIC_MESSAGES` 原生请求 Anthropic `/v1/messages`。Claude 使用 `provider: anthropic` 和 `ANTHROPIC_MESSAGES`，不会经由 OpenAI-compatible 转发。

协议层以 Spring 注入的 `ModelProtocolAdapter` 为 SPI：每个 Adapter 自报 `protocolId()` 并负责将协议特有请求和响应转换为统一的 `AgentTurnRequest` / `AgentTurnResult`。`ModelProtocolAdapterRegistry` 仅按 YAML 中的 `protocol` 查找 Adapter；游戏 Harness、Agent Controller、模型档案管理和 Probe 不按厂商名称分支。未来 OpenAI 出现新协议时，新增一个 Adapter 并在模型 YAML 中声明新 protocol 即可，不需要修改核心路由。

Spring AI 作为可选适配器存在，主要用途是：

- 学习框架如何实现 ChatClient、Advisor、Tool Calling 和 Observability。
- 对比自有 Harness 与框架 Harness 的职责边界。
- 未来复用 Spring AI 已支持的 Provider。

任何情况下，`GameRuleEngine`、`PlayerController` 和 Agent Memory 都不能依赖 Spring AI。

### 1.1 当前实现状态

本项目当前未引入 Spring AI，也没有实现本章后续所述的通用 Typed Item、Tool Calling、Provider 状态续接和 Capability 协商。三个现有协议已经统一使用 SSE 流式请求和逐帧聚合；流式传输是当前可用能力，不再是后续目标。

当前可用协议仅有：

| protocol | 原生端点 | 当前 Adapter | 流事件 |
| --- | --- | --- | --- |
| `OPENAI_RESPONSES` | `/v1/responses` | `OpenAiResponsesGateway` | typed response/reasoning/output events |
| `OPENAI_COMPATIBLE_CHAT` | `/v1/chat/completions` | `OpenAiChatCompletionsGateway` | delta 中的 content/reasoning 字段 |
| `ANTHROPIC_MESSAGES` | `/v1/messages` | `AnthropicMessagesGateway` | message/content block/usage events |

每个档案位于 `avalon-app/src/main/resources/model-profiles/<modelId>.yml`，其实际配置结构为：

```yaml
modelId: claude-sonnet-4-6
displayName: Claude Sonnet 4.6
provider: anthropic
protocol: ANTHROPIC_MESSAGES
modelName: claude-sonnet-4-6
temperature: 0.2
enabled: false
providerOptions:
  baseUrl: https://api.anthropic.com/v1
  apiKeyEnv: ANTHROPIC_API_KEY
  anthropicVersion: 2023-06-01
  maxOutputTokens: 8192
```

`providerOptions` 是协议实现的私有配置。`ANTHROPIC_MESSAGES` 要求 `maxOutputTokens`，因为 Anthropic 的 `max_tokens` 是请求必填字段；它不等于项目级默认 token 限制，也不会被其他协议自动继承。

模型档案在启动时以及托管档案创建、更新时由 `ModelProtocolAdapterRegistry` 校验；没有注册 Adapter 的 `protocol` 会被拒绝。模型 Probe 同样通过该注册表执行实际协议 Adapter，而非自行判断 OpenAI 或 Anthropic。

## 2. 为什么默认使用 Responses API

相较 Chat Completions，Responses API 更适合 Agent Harness：

- 输入和输出由 Typed Items 表达。
- 原生支持工具调用及工具结果关联。
- 支持 Structured Outputs。
- 支持 reasoning items 和 reasoning summaries。
- 可通过 `previous_response_id` 或 Conversations API 管理连续状态。
- 支持流式 typed events。
- 可以接入 OpenAI 托管工具，但本项目默认只开放受控自定义工具。

旧项目使用 Chat Completions 和 `response_format`。新适配器需要使用 Responses API 的 `text.format` 语义，不继续扩展旧协议模型。

## 3. 当前 Model Protocol SPI

```java
public interface ModelProtocolAdapter extends AgentGateway {
    String protocolId();
}
```

`RoutingAgentGateway` 只将 `request.protocol` 交给注册表；`provider: noop` 仍用于本地非 LLM 玩家。所有外部模型协议由 Adapter 自己处理认证、端点、请求映射、响应解析和元数据归一化，Adapter 不得决定游戏动作是否合法。

新增协议的步骤是：实现 `ModelProtocolAdapter`、以 Spring Bean 注册、在 YAML 写入其 `protocol`，再为其协议专属必填配置提供校验。无需修改 Harness、游戏规则或 `RoutingAgentGateway`。

### 3.1 归一化响应边界

协议 Adapter 负责把 HTTP、SSE 或未来 SDK 回调收到的 Provider 事件归一化为同一个
`AgentTurnResult`。传输方式不得泄漏到 Harness：Harness 不关心响应来自一次性 HTTP body、SSE
增量事件还是 SDK Publisher，只关心最终聚合后的正文、动作候选、可选认知区段、完成原因、用量和
诊断元数据。

归一化不代表信任模型内容。Adapter 只负责协议完整性和 DTO 解码；最终动作是否合法由 Harness 和
规则引擎判断，可选认知草稿是否合法由 Memory/Cognition Policy 判断。

同一个响应中的字段采用不同失败边界：

| 区段 | 必需性 | 失败行为 |
| --- | --- | --- |
| 最终动作 | 必需 | 分类修复重试；耗尽后按 Failure Policy 处理 |
| 公开发言 | 当前阶段要求时必需 | 按动作契约处理 |
| Audit / Decision Summary | 可选 | 丢弃并记录告警 |
| Memory / Belief / Strategy / Communication | 可选草稿 | 独立校验，失败时丢弃且不重试动作 |
| Provider reasoning | 非产品契约 | 仅作受限诊断，不参与动作或认知提交 |

因此 Provider Adapter 不得因为某个可选区段无法转换而丢失一个已经可解码的动作；Harness 也不得
因为可选认知草稿非法而重复提交模型决策。

## 4. OpenAI Responses Adapter

### 4.1 请求映射

逻辑字段映射：

| Model SPI | OpenAI Responses |
| --- | --- |
| `target.model` | `model` |
| `InstructionItem` | 顶层 `instructions` 或对应 input item |
| `input` | `input` typed items |
| `tools` | function tools |
| `output.schema` | `text.format` Structured Output |
| `options.reasoningEffort` | `reasoning.effort` |
| `continuation.responseId` | `previous_response_id` |
| `metadata` | `metadata` |

### 4.2 当前限制

当前实现使用 `text.format.type: json_object` 请求 JSON 输出并解析为游戏动作，并通过 `stream: true` 消费 `response.output_text.delta`、reasoning delta 和 `response.completed`。尚未实现 `function_call`、`previous_response_id`、Conversations API 或 provider 托管工具。

## 5. OpenAI-compatible Chat Adapter

此 Adapter 仅适用于 YAML **明确**声明 `OPENAI_COMPATIBLE_CHAT` 的服务。它发送带 `stream: true` 的 `messages` 到 `/v1/chat/completions`，逐帧识别 `content`、`reasoning_content`、`reasoning`、`reasoning_text` 和 `thinking`；它不表示模型或厂商天然支持 OpenAI Responses。

## 6. Anthropic Messages Adapter

`ANTHROPIC_MESSAGES` 使用 Anthropic 原生 Messages 协议，不经 OpenAI 兼容层。请求使用 `x-api-key`、`anthropic-version` 和 `messages`，响应从 `content[type=text]` 提取 JSON 动作，并记录 `input_tokens`、`output_tokens` 和 `stop_reason`。

当前通过 Anthropic 原生 SSE 消费 `message_start`、`content_block_delta`、`message_delta` 和 `message_stop`，并区分 `thinking_delta` 与 `text_delta`。未实现 Anthropic Tools、Extended Thinking 全文持久化或多轮工具循环。

## 6.1 统一 SSE 传输契约

所有生产 Adapter 共享原始 SSE 帧传输，但各自维护协议状态机：

```text
HTTP status / retry-before-first-frame
-> SSE frame(event, data)
-> protocol-specific accumulator
-> ModelStreamEvent
-> terminal validation
-> AgentTurnResult
```

Transport 不提供非流式 JSON 入口，也不允许把完整 JSON 响应伪装成 SSE 帧。Provider 即使不返回 reasoning，也必须以 `text/event-stream` 返回正文和终止事件；成功响应的媒体类型不是 `text/event-stream` 时，应按协议错误终止。reasoning 分片是供应商公开的调试输出或摘要，不保证等于模型隐藏的完整思维链。

`COMPLETED` 只能在协议终止事件完整、最终正文已成功解码为 `AgentTurnResult` 后发布；SSE 中断、终止事件缺失或最终 JSON 解码失败都必须发布 `FAILED`。这里的 `COMPLETED` 仅表示 Provider Adapter 已完成，不代表 Harness 或规则引擎已经接受动作。

## 7. 目标架构：结构化输出

每个动作阶段生成专用 JSON Schema。例如投票阶段只允许：

```json
{
  "type": "object",
  "properties": {
    "publicSpeech": { "type": "string" },
    "action": {
      "type": "object",
      "properties": {
        "type": { "const": "TEAM_VOTE" },
        "vote": { "enum": ["APPROVE", "REJECT"] }
      },
      "required": ["type", "vote"],
      "additionalProperties": false
    }
  },
  "required": ["action"],
  "additionalProperties": false
}
```

不能用一个包含所有阶段字段的巨型 Schema，否则模型更容易选择无关字段。

### 7.1 目标：连续状态

支持三种模式：

- `STATELESS_REPLAY`：本地构建完整必要输入。
- `PREVIOUS_RESPONSE_ID`：保存并链接前次响应。
- `CONVERSATION`：使用 Provider 持久 Conversation。

默认模式是 `STATELESS_REPLAY`。启用后两者时仍要保存本地上下文、事件与 Memory，并具备无 Provider 状态恢复路径。`previous_response_id` 和 Provider Conversation 必须按 `gameId + ownerPlayerId + agentInstanceId` 隔离；相同 Agent Profile 的两个座位也不能共享会话。

顶层 `instructions` 在使用 `previous_response_id` 时仍应每次重新发送。

### 7.2 目标：存储策略

Provider 请求是否 `store` 由配置决定，不由 Agent 自行选择。需要零数据保留时使用 `store: false`，并按协议保存和重放必要的加密 reasoning items。本地 `agent_model_request` 与可选 payload 同样属于玩家私有执行数据，不因 Provider 启用存储而变成共享上下文；详细保留策略见[持久化存储设计与 Phoenix 借鉴](11-持久化存储设计与Phoenix借鉴.md)。

### 7.3 目标：最终动作提交通道

模型可以使用两种协议形式表达最终游戏动作：

```text
STRUCTURED_OUTPUT（默认）
FUNCTION_CALL（兼容模式）
```

认知工具调用可以发生零次或多次；最终动作必须恰好一次。Function Call 模式中的 `submit_team_vote`、`submit_mission_choice` 等函数只能映射为 `ProposedAction`，不能直接修改 Game、Action Batch 或数据库。

同一回合不得同时通过 Structured Output 和 Function Call 提交两个动作。具体批次和幂等规则见 [GameCoordinator 与动作收集规范](12-GameCoordinator与动作收集.md)。

## 8. 目标架构：Spring AI Adapter

Spring AI 2.0.x 适配器实现相同 `ModelClient`：

```text
ModelRequest
-> Spring AI Prompt / ChatOptions / ToolCallbacks
-> ChatClient or ChatModel
-> Spring AI response
-> ModelResponse
```

### 8.1 可复用能力

- ChatClient fluent API
- ToolCallback 和动态 Tool Resolver
- Advisor 链
- Structured Output Converter
- Micrometer Observability
- Provider Starter

### 8.2 必须隔离的部分

- Spring AI `Message` 不进入 Harness 公共接口。
- Spring AI ChatMemory 不成为 Agent Memory 的权威存储。
- Advisor 不直接读取完整游戏聚合。
- ToolCallback 必须复用项目的 Tool Policy 和权限上下文。
- Spring AI 自动重试不得与 Harness 重试叠加为不可控次数。

### 8.3 适配策略

第一阶段不要求 Spring AI Adapter 覆盖所有 OpenAI Responses 特性。它可以声明自己的 `ModelCapabilities`，Harness 根据能力选择兼容路径。

## 9. 目标架构：Capability 模型

```java
public record ModelCapabilities(
        boolean structuredOutput,
        boolean strictStructuredOutput,
        boolean toolCalling,
        boolean parallelToolCalling,
        boolean reasoningEffort,
        boolean reasoningSummary,
        boolean statefulContinuation,
        boolean streaming,
        OptionalInt contextWindowTokens,
        OptionalInt maxOutputTokens
) {}
```

启动时比较 Agent/Harness 需求与模型能力：

- 需要 Tool Calling 但模型不支持：配置失败。
- 不支持 Strict Structured Output：允许使用解析加校验兼容模式，但必须显式开启。
- 上下文窗口小于 Harness 最低预算：配置失败。

## 10. 目标架构：错误模型

统一错误分类：

```text
AUTHENTICATION
AUTHORIZATION
INVALID_REQUEST
MODEL_NOT_FOUND
CAPABILITY_MISMATCH
RATE_LIMITED
CONTEXT_LENGTH_EXCEEDED
CONTENT_FILTERED
TIMEOUT
NETWORK
PROVIDER_UNAVAILABLE
MALFORMED_RESPONSE
STREAM_INTERRUPTED
UNKNOWN_PROVIDER_ERROR
```

`STREAM_INTERRUPTED` 的重试边界是首帧：首帧之前可由 HTTP Transport 重试；首帧之后只能由 Harness 创建一次新的 Model Request Attempt，旧分片不得拼接到新请求结果中。Transport 必须使用模型档案的 `timeoutMillis` 同时约束连接建立和 SSE 流读取；到达读取 Deadline 后必须关闭响应流，禁止玩家回合无限等待。

错误对象包含：

- 可重试性建议
- Provider 错误码
- HTTP 状态
- Retry-After
- 请求 ID
- 是否可能已产生计费
- 已接收的部分使用量

Harness 最终决定重试和失败策略。

## 15. 目标架构：凭据管理

普通 YAML 中只允许 `credentialRef`：

```text
env:OPENAI_API_KEY
file:C:/secure/avalon-secrets.yml#providers.openai-main.apiKey
systemProperty:avalon.provider.openai.api-key
```

解析优先级：

```text
explicit startup override
> environment variable
> external secrets file
> system property
```

不提供 classpath 默认密钥。日志、异常、Trace 和配置查询接口必须脱敏。

## 16. 目标架构：配置分层与冻结

配置文件分为：

- Provider Registry
- Model Registry
- Agent Registry
- Harness Registry
- Skill Registry
- Rule Pack Registry
- Game Preset

创建游戏时解析引用；开始游戏时冻结：

- Agent Profile 完整内容
- Model Profile 完整内容
- Provider 非秘密配置
- Harness、Skill 和 Memory Policy 版本
- Rule Pack 版本与 Hash

API Key 不进入游戏快照，只保存 Credential Ref。

## 17. 目标架构：配置校验

启动校验：

- ID 唯一。
- 引用存在。
- Provider 类型已注册。
- Model 能力满足 Harness 要求。
- Skill 版本存在且无冲突。
- Harness 预算合理。
- Credential Ref 格式合法。

开局校验：

- 所有 LLM 座位能解析 Agent。
- Provider 已启用。
- 角色/阶段需要的 Skill 可解析。
- 预算不会超过系统级上限。
- 可选执行 Provider Probe，但不能强制产生高成本调用。

## 18. 目标架构：配置覆盖

统一优先级：

```text
command line
> environment
> external config directory
> classpath defaults
```

运行中的游戏不自动吸收新配置。新配置只影响后续创建或显式迁移的游戏。

## 19. 当前实现：启用模型池与随机席位分配

`avalon-app/src/main/resources/model-profiles/` 下的每个模型档案都有 `enabled` 开关。它既决定模型是否可以被手工绑定，也决定它是否进入默认随机池。

控制台创建 LLM 对局时，默认选模方式是 `random`。不传 `candidateModelIds` 时，系统读取所有 `enabled: true` 的档案，并按候选档案顺序对 LLM 席位轮询分配；席位数超过模型数时从第一个档案继续循环，因此模型数量不需要等于玩家数量，允许一个档案被多个席位复用。

例如，5 人 LLM 局只启用 `glm-5` 和 `deepseek-chat`，则席位依次绑定 `glm-5`、`deepseek-chat`、`glm-5`、`deepseek-chat`、`glm-5`。所有未配置密钥或仅作为参考的模板必须设为 `enabled: false`，以免被模型池选中。

```yaml
# glm-5.yml
enabled: true
providerOptions:
  apiKeyEnv: GLM_API_KEY

# deepseek-chat.yml
enabled: true
providerOptions:
  apiKeyEnv: DEEPSEEK_API_KEY
```

密钥通过环境变量或外部 secrets 文件提供，不能写入版本控制中的 YAML。角色、Harness、记忆和会话命名空间仍按席位独立创建；复用同一模型档案不会让两个席位共享私有上下文。

## 20. 当前实现：模型 Probe

提供只读诊断命令：

```text
probe-model <modelId> [connectivity|structured|all]
```

Probe 结果报告：

- 连接和鉴权
- 实际模型 ID
- Structured Output
- 延迟和协议 Adapter 提供的完成原因

Probe 通过目标档案的 `ModelProtocolAdapter` 发送一次规范化动作请求，因此路由与实际游戏一致。当前不探测 Tool Calling、流式响应、Provider 模型列表或模型能力上限；Probe 不会自动更改配置。
