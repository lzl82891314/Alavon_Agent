# 06 - 编排、持久化与交付通道

## 1. 应用层职责

应用层负责把领域、控制器、Harness 和持久化组合成可运行用例：

- 创建游戏
- 验证并冻结配置
- 开始游戏
- 请求下一位玩家行动
- 提交玩家行动
- 自动运行到等待态或结束态
- 暂停、恢复和取消
- 查询公共、私有、管理员和回放视图

应用层不复制规则。如果需要知道下一阶段，必须询问或应用领域事件，而不是自己判断任务胜负。

## 2. 用例接口

```java
public interface GameCoordinator {
    CreateGameResult create(CreateGameCommand command);
    GameView start(StartGameCommand command);
    AdvanceResult advance(AdvanceGameCommand command);
    SubmitActionResult submit(SubmitPlayerActionCommand command);
    GameView pause(PauseGameCommand command);
    GameView resume(ResumeGameCommand command);
}

public interface GameQueryService {
    PublicGameView publicView(String gameId);
    PlayerPrivateView playerView(String gameId, String playerId);
    AdminGameView adminView(String gameId);
    ReplayView replay(String gameId);
}
```

Console 和 Web 只调用这些接口。

`GameCommandService` 如需保留，只能作为委托给 `GameCoordinator` 的薄门面，不能存在第二套推进逻辑。

## 3. 游戏推进算法

```text
load aggregate
-> load active Action Batch when present
-> otherwise ask domain for NextRequirement
-> automatic requirement: apply transition
-> action requirement: open persistent Action Batch
-> resolve required Player Controllers against frozen input snapshot
-> collect submissions privately
-> completed batch: domain validates and emits events
-> append events atomically
-> mark batch committed
-> update snapshot when policy requires
-> publish filtered application events
```

### 3.1 自动运行

`run` 不是一个不可中断的大循环，而是反复调用 `advance`：

```java
while (result.canAutoContinue() && withinSafetyBudget()) {
    result = commandService.advance(command);
}
```

停止条件：

- 游戏结束
- 等待真人动作
- LLM 失败导致暂停
- 达到调用次数或时间安全限制
- 操作者请求单步停止

## 4. Controller 解析

```java
public interface PlayerControllerResolver {
    PlayerController resolve(GameConfigurationSnapshot game, GamePlayer player);
}
```

玩家类型：

| 类型 | 行为 |
| --- | --- |
| `LLM` | 调用 Agent Harness |
| `HUMAN` | 创建持久等待请求 |
| `SCRIPTED` | 使用确定性策略 |
| `REMOTE` | 未来调用外部 Agent 服务 |

Controller 类型属于座位配置，不属于角色定义。

## 5. Human 玩家等待态

真人玩家不是 Console 特例。当轮到 Human 时：

1. 应用层创建 `PendingPlayerAction`。
2. 游戏进入 `WAITING_FOR_PLAYER_ACTION`。
3. 保存 Turn Token、动作 Schema、截止时间和玩家 ID。
4. Console、REST 或未来 GUI 展示同一请求。
5. 外部提交 `SubmitPlayerActionCommand`。
6. 应用层检查身份、版本和 Turn Token。
7. 领域规则引擎校验并推进游戏。

Human 可以与 LLM、Scripted 玩家共同存在于一个 Parallel Action Batch。其他玩家已提交的投票或任务选择在 Batch 完成前不得向 Human 或任何 Agent 披露。

```java
public record PendingPlayerAction(
        String gameId,
        TurnToken turnToken,
        PlayerId playerId,
        AllowedActionSet allowedActions,
        Instant createdAt,
        Optional<Instant> expiresAt
) {}
```

完整的单人、并行动作和混合 Controller 调度见 [GameCoordinator 与动作收集规范](12-GameCoordinator与动作收集.md)。

## 6. Event Store

事件是游戏状态变化的权威记录：

```sql
game_event(
  game_id,
  sequence_no,
  aggregate_version,
  event_type,
  event_version,
  visibility,
  actor_id,
  payload_json,
  occurred_at,
  correlation_id,
  causation_id
)
```

关键约束：

- `(game_id, sequence_no)` 唯一。
- 使用 `expectedVersion` 乐观并发追加。
- Payload 带 Event Version，支持未来 upcaster。
- 私密事件的查询必须通过服务端投影过滤。

## 7. Snapshot

快照用于加速恢复，不替代事件：

```sql
game_snapshot(
  game_id,
  aggregate_version,
  snapshot_version,
  state_json,
  configuration_snapshot_json,
  created_at
)
```

快照策略：

- 开局角色分配后保存。
- 每个任务轮次结束后保存。
- 游戏暂停或结束时保存。
- 事件数量超过阈值时保存。

恢复流程：

```text
load latest snapshot
-> load events after snapshot version
-> apply events
-> rebuild projections
-> restore active Action Batch and completed submissions
-> retry only missing controller executions or uncommitted domain submission
-> restore pending action and agent memory references
-> restore per-player observation cursor, belief and strategy state
```

## 8. Agent Memory Store

Memory 与游戏事件分开存储，但引用事件 Sequence：

```sql
player_memory(
  game_id,
  owner_player_id,
  agent_instance_id,
  memory_id,
  memory_kind,
  subject_player_id,
  summary,
  evidence_refs_json,
  confidence,
  created_at_sequence,
  expires_after_sequence,
  memory_version
)
```

Memory 不是领域真相。恢复游戏时可以缺少非关键 Memory，但不能缺少领域事件。

### 8.1 Strategic State Store

战略状态独立于领域聚合，但属于 Agent 可恢复运行状态：

```sql
player_cognition_state(
  game_id,
  owner_player_id,
  agent_instance_id,
  state_version,
  last_observed_sequence,
  belief_state_json,
  strategy_state_json,
  public_commitments_json,
  cover_story_json,
  updated_at
)
```

持久化约束：

- `(game_id, owner_player_id, agent_instance_id)` 唯一；同一 Agent Profile 的不同座位不共享状态。
- `last_observed_sequence` 只能单调递增。
- Belief State 必须保存 Evidence Ref，不能只保存最终概率。
- Cover Story 和 Deception Plan 仅允许玩家本人和管理员读取。
- Public Commitment 来源于公开事件，可以在恢复时重建，但仍建议缓存。
- Strategic State 丢失时必须从可见事件重建或暂停，不能静默初始化为空继续游戏。

### 8.2 双通道记忆提交

每次 Agent 回合使用“私有 Draft -> 规则接受 -> 正式状态”的提交顺序：

1. 宿主从公开事件确定性生成 Observation/Commitment，并写入当前玩家作用域的 Run 或认知状态。
2. Belief/Strategy/Communication Plan 先作为当前 `AgentRun` 的私有 Draft 保存。
3. `GameRuleEngine` 接受动作或完整 Action Batch 后，才在对应提交事务中写入正式 Belief/Strategy 和 Checkpoint。
4. 如果 Turn Token、Game Version 或规则校验失败，Run 标记为 `SUPERSEDED` 或 `FAILED`；它的 Draft 不得覆盖正式状态。

模型没有返回 Memory Proposal 时，第一条通道仍必须推进观察游标并保存公开事实。每次读取和写入都必须带 `gameId + ownerPlayerId + agentInstanceId`，不能只按 `gameId` 查询。

## 9. Agent Trace 与 Audit

```sql
agent_run(

  owner_player_id,
  agent_instance_id,
  turn_token,
  base_game_version,
  observed_from_sequence,
  observed_through_sequence,
  private_view_fingerprint,

  status,
  started_at,
  completed_at,
  total_latency_ms,
  input_tokens,
  output_tokens,
  estimated_cost,
  failure_type
)
```

详细 Trace 可以拆分：

- `agent_run_artifact`
- `agent_model_request`
- `agent_tool_call`
- `agent_validation_result`
- `agent_context_manifest`
- `agent_decision_summary`

原始请求/响应是否保存由 Audit Level 和数据策略控制，默认保存脱敏后的结构化摘要与 Hash。
Run、Tool Call、Model Request、Belief、Strategy 和 Checkpoint 都是玩家私有数据；管理员审计查询也不注册为 Agent Tool。完整存储布局见[持久化存储设计与 Phoenix 借鉴](11-持久化存储设计与Phoenix借鉴.md)。

## 10. 事务边界

模型调用不得长期占用数据库事务。

推荐流程：

```text
Transaction A:
  load game
  resolve NextRequirement
  create persistent Action Batch with frozen input snapshot
  commit

Outside transaction:
  execute controller / model

Transaction B:
  load Action Batch
  verify batch version, player and idempotency key
  persist one Action Submission
  update batch status
  commit

Transaction C, only when batch is complete:
  load game and Completed Action Batch
  verify source game version and turn token
  ask GameRuleEngine to decide
  append resulting events
  mark Action Batch committed
  commit
```

这可以避免慢调用锁住数据库，同时通过 Game Version、Batch Version、Turn Token 和 Idempotency Key 处理并发。详细恢复和失效规则见 [GameCoordinator 与动作收集规范](12-GameCoordinator与动作收集.md)。

## 11. 幂等性

所有外部命令携带 `idempotencyKey`：

- 相同 Key、相同 Payload：返回第一次结果。
- 相同 Key、不同 Payload：返回冲突。
- Provider 重试使用新的 Provider Request ID，但归属于同一个 Agent Execution。
- Human 重复点击不会产生两次投票。

## 14. SSE 事件流

```text
GET /api/games/{gameId}/stream?view=public
GET /api/games/{gameId}/stream?view=player
GET /api/games/{gameId}/stream?view=admin
```

事件 Envelope：

```json
{
  "eventId": "game-1:42",
  "gameId": "game-1",
  "sequence": 42,
  "type": "TEAM_APPROVED",
  "visibility": "PUBLIC",
  "occurredAt": "2026-08-07T10:00:00Z",
  "payload": {}
}
```

SSE 支持 `Last-Event-ID`，客户端断线后从 Sequence 继续。服务端按认证身份生成投影，不能把管理员事件发给普通流后再让前端隐藏。

## 15. 未来 GUI

未来前端只需要：

- REST 创建、查询和提交动作。
- SSE 接收游戏事件。
- 根据 `AllowedActionSet` 渲染按钮或表单。
- 根据 Public/Player View 渲染不同信息。

前端不实现：

- 阶段推进
- 合法性规则
- 角色知识计算
- Agent 调用
- 胜负判断

因此 Console 版本完成后，增加 GUI 不需要重写核心。

## 16. 回放

回放从事件流生成，不重新调用模型：

- 按 Sequence 展示公共事件。
- 游戏结束前隐藏仍然保密的字段。
- 游戏结束后是否揭示全部角色由 Rule Pack 和查看权限决定。
- 管理员可以关联查看 Agent Execution 和 Decision Summary。
- 支持导出 JSON Lines，便于离线评测。

## 17. 恢复场景

必须支持：

- 应用在等待 LLM 时重启。
- 应用在等待 Human 时重启。
- Provider 调用成功，但动作提交前进程崩溃。
- 快照存在但后续有未投影事件。
- Agent 配置文件在游戏过程中被修改。

恢复原则：

- 领域事件决定游戏状态。
- 冻结配置决定当前游戏使用的规则和 Agent。
- 未完成 Agent Execution 可以标记为中断并重新调度。
- 已完成但未提交的动作必须通过 Turn Token 和幂等键安全重交。

## 18. 数据保留

建议分级：

| 数据 | 默认保留 |
| --- | --- |
| 领域事件和结果 | 长期 |
| 游戏快照 | 可按策略清理旧版本 |
| Agent 决策摘要 | 长期或评测周期 |
| 原始 Provider 输入输出 | 默认关闭或短期 |
| Provider Opaque Reasoning | 按协议和隐私策略 |
| Metrics | 时序库保留策略 |

删除原始模型内容不得破坏游戏回放。
