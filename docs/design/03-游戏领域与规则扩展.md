# 03 - 游戏领域与规则扩展

## 1. 设计目标

游戏领域层负责回答三个问题：

1. 当前权威状态是什么？
2. 某个命令在当前状态下是否合法？
3. 合法命令会产生哪些领域事件？

它不负责：

- 决定 Agent 如何思考。
- 调用模型。
- 拼接 Prompt。
- 读取 Console 输入。
- 保存 JPA Entity。

## 2. 聚合边界

`Game` 是核心聚合根。所有改变游戏事实的行为必须通过聚合或规则引擎完成。

```java
public final class Game {
    private final GameId id;
    private final RulePackRef rulePack;
    private final List<GamePlayer> players;
    private GameStatus status;
    private GamePhase phase;
    private int round;
    private long version;
    private GameBoard board;
}
```

聚合中保存的是推进游戏所需的最小权威状态，不保存完整 Prompt、HTTP 响应或 Console 展示字符串。

## 3. 状态与阶段

### 3.1 GameStatus

```text
CREATED
READY
RUNNING
WAITING_FOR_CONTROLLER
WAITING_FOR_PLAYER_ACTION
PAUSED
ENDED
CANCELLED
```

`GameStatus` 表示生命周期；`GamePhase` 表示规则阶段。二者不能混为一个枚举。

### 3.2 默认阶段图

```text
ROLE_REVEAL
    |
    v
ROUND_START
    |
    v
DISCUSSION
    |
    v
TEAM_PROPOSAL
    |
    v
TEAM_VOTE -- rejected --> DISCUSSION(next leader)
    |
 approved
    v
MISSION_ACTION
    |
    v
MISSION_RESOLUTION
    |
    +-- next round --> ROUND_START
    +-- good has 3 successes --> ASSASSINATION
    +-- evil has 3 failures --> GAME_END
```

阶段图属于 Rule Pack，不应把所有转换写死在一个巨大 `switch` 中。

### 3.3 讨论子阶段

`DISCUSSION` 不能实现成每位玩家固定说一句的独白循环。经典规则包默认包含以下受控子阶段：

```text
OPENING_STATEMENTS
-> CHALLENGE_WINDOW
-> TARGETED_RESPONSES
-> LEADER_SYNTHESIS
-> TEAM_PROPOSAL
```

讨论调度属于游戏机制，决定谁可以在何时发言、质疑和回应；发言内容属于 Player Controller。默认讨论必须有次数、时间和 Token 上限，避免无限对话。

完整约束见 [战略认知与社会博弈规范](10-战略认知与社会博弈.md)。

## 4. 命令、候选动作与领域事件

### 4.1 Command

Command 是调用者希望系统执行的意图：

- `CreateGame`
- `StartGame`
- `SubmitPublicSpeech`
- `ProposeTeam`
- `CastTeamVote`
- `SubmitMissionChoice`
- `SubmitAssassinationTarget`
- `PauseGame`
- `ResumeGame`
- `CancelGame`

### 4.2 ProposedAction

玩家控制器返回 `ProposedAction`。它尚未成为事实：

```java
public sealed interface ProposedAction permits
        PublicSpeechProposal,
        TeamProposal,
        TeamVoteProposal,
        MissionChoiceProposal,
        AssassinationProposal {
    PlayerId playerId();
    ActionType actionType();
    TurnToken turnToken();
}
```

`turnToken` 用于拒绝过期、重复或来自错误回合的异步结果。

### 4.3 DomainEvent

领域事件是已经发生的事实：

- `GameCreated`
- `PlayersSeated`
- `RolesAssigned`
- `GameStarted`
- `DiscussionOpened`
- `PlayerSpoke`
- `PlayerChallenged`
- `PlayerResponded`
- `LeaderSummarized`
- `TeamProposed`
- `TeamVotesRevealed`
- `TeamApproved`
- `TeamRejected`
- `MissionChoiceSubmitted`
- `MissionSucceeded`
- `MissionFailed`
- `AssassinationOpened`
- `AssassinationResolved`
- `GamePaused`
- `GameEnded`

私密动作事件可存储完整事实，但公共投影必须隐藏任务票来源等秘密信息。

## 5. 规则引擎

```java
public interface GameRuleEngine {
    NextRequirement nextRequirement(GameState state);
    DecisionResult decide(GameState state, GameCommand command);
}

public record DecisionResult(
        List<GameEvent> events,
        Optional<NextRequirement> nextRequirement,
        List<RuleNotice> notices
) {}
```

规则引擎采用“输入状态 + 命令 -> 事件”的形式，便于回放、调试和确定性验证。

### 5.1 校验层次

1. 结构校验：必填字段、枚举、集合大小。
2. 身份校验：玩家是否存在、是否轮到该玩家。
3. 阶段校验：当前阶段是否允许此动作。
4. 规则校验：队伍人数、好人任务票、目标范围等。
5. 并发校验：游戏版本和 Turn Token 是否匹配。

任何校验失败都不得产生部分领域事件。

## 6. Phase Handler 扩展

```java
public interface PhaseHandler {
    String phaseType();
    AllowedActionSet allowedActions(GameState state);
    DecisionResult handle(GameState state, GameCommand command);
    Optional<PhaseTransition> autoTransition(GameState state);
}
```

默认实现：

- `DiscussionPhaseHandler`
- `TeamProposalPhaseHandler`
- `TeamVotePhaseHandler`
- `MissionActionPhaseHandler`
- `MissionResolutionPhaseHandler`
- `AssassinationPhaseHandler`

新增湖中仙女等机制时，可以增加新 Handler 和阶段定义，而不修改 LLM Provider。

## 7. Rule Pack

Rule Pack 是一套可版本化游戏机制：

```yaml
rulePackId: avalon-classic
version: 1.0.0
playerRange:
  min: 5
  max: 10
phaseGraph: classic-phase-graph
setupTemplateIds:
  - classic-5p
  - classic-6p
victoryConditionIds:
  - mission-score
  - merlin-assassination
```

对局必须保存精确的 `rulePackId + version + contentHash`。不能只保存一个可能被覆盖的文件名。

## 8. Setup Template

Setup Template 决定固定人数下的角色构成：

```yaml
setupId: classic-5p
rulePack: avalon-classic@1.0.0
playerCount: 5
roles:
  - MERLIN
  - PERCIVAL
  - LOYAL_SERVANT
  - MORGANA
  - ASSASSIN
```

5 至 10 人标准局通过增加 Setup Template 和对应任务表完成。当前项目只内置基础版阿瓦隆的标准人数范围；11 人及以上属于独立变体，不作为经典规则包的一部分。

## 9. Role Definition

```yaml
roleId: MERLIN
camp: GOOD
tags:
  - SPECIAL_GOOD
knowledgeRules:
  - type: SEE_PLAYERS_BY_CAMP
    camp: EVIL
    excludeRoleTags:
      - HIDDEN_FROM_MERLIN
winConditionContribution: GOOD
```

角色定义包含：

- 阵营
- 标签
- 私有知识规则
- 特殊动作能力
- 胜负贡献
- 可选的阶段修饰器

角色本身不包含 Agent 人格。Agent Profile 和随机角色分配必须分离。

## 10. 可见性系统

### 10.1 权威事实与视图区分

系统内部可以知道所有角色，但任何控制器只能收到自己的 `PlayerPrivateView`。

```java
public interface PlayerViewProjector {
    PlayerPrivateView project(GameState state, PlayerId viewer);
}
```

### 10.2 PlayerPrivateView

包含：

- 公共游戏快照
- 自己的座位、角色和阵营
- 角色规则允许看到的其他玩家信息
- 自己参与的秘密动作确认
- 当前允许动作
- 不透明的回合标识

禁止包含：

- 其他玩家完整角色
- 任务失败票来源
- 其他 Agent 的记忆
- 管理员审计记录
- 未公开的 Provider 输出

### 10.3 视图来源追踪

每条私有知识都带来源：

```java
public record KnowledgeFact(
        String factType,
        Map<String, Object> value,
        String sourceRuleId,
        VisibilityLevel visibility
) {}
```

这样可以审计某条信息为什么出现在 Agent 上下文中。

## 11. 默认 5 人规则

默认规则：

| 轮次 | 任务人数 | 失败阈值 |
| --- | ---: | ---: |
| 1 | 2 | 1 |
| 2 | 3 | 1 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 1 |

其他默认行为：

- 连续 5 次组队投票失败，邪恶阵营获胜。
- 好人完成 3 次成功任务后进入刺杀阶段。
- 刺客命中梅林则邪恶阵营获胜，否则好人获胜。
- 好人不得提交失败任务票。

这些值来自 Rule Pack，领域代码不写死“5 人局”。

## 12. 6 至 10 人标准扩展

人数扩展需要配置：

- 人数范围
- 角色列表
- 每轮任务人数
- 每轮失败阈值
- 特殊角色启用规则
- 投票和胜负变体

标准 7 人及以上第四轮双失败规则应表现为数据：

```yaml
missionFailThresholds:
  1: 1
  2: 1
  3: 1
  4: 2
  5: 1
```

11 人及以上的非标准变体必须使用独立 Rule Pack 命名空间、独立任务表和角色配比；当前项目不内置这类规则，也不将其伪装成官方经典规则。

## 13. 声明式与代码式规则的边界

适合 YAML：

- 人数、角色、任务人数和阈值
- 阶段顺序
- 简单可见性过滤
- 组件引用
- 开关与参数

适合 Java：

- 复杂阶段交互
- 非平凡胜负条件
- 需要领域类型保护的动作转换
- 高复杂度知识规则

不得尝试在 YAML 中发明一门任意脚本语言。

## 14. Rule Pack 校验

启动和创建游戏时必须验证：

- Setup 人数与角色数量一致。
- 阵营比例符合 Rule Pack 限制。
- 引用的角色、阶段、胜负条件存在。
- 阶段图存在起点、终点且没有不可达阶段。
- 每轮任务人数不超过玩家数。
- 失败阈值不超过任务人数。
- 刺杀规则引用的角色真实存在。
- 可见性规则不会引用未知标签。
- Rule Pack 版本与 Hash 唯一。

## 15. 随机性与可复现性

所有影响游戏真相的随机行为使用游戏 seed 派生：

- 角色洗牌
- 初始队长
- 随机 Agent 池绑定

模型输出本身不保证可复现，但角色分配和规则结果必须可复现。对局开始后保存实际分配结果，而不是恢复时重新抽取。

## 16. 事件投影

同一事件流产生不同投影：

| 投影 | 用途 |
| --- | --- |
| Public Game View | Console、观众和公开 API |
| Player Private View | 某个玩家或 Agent |
| Admin View | 调试和审计 |
| Replay View | 对局结束后的时间线 |
| Evaluation View | Harness 和模型评测 |

投影层负责隐藏字段，不能要求客户端自行过滤秘密信息。

## 17. 并发控制

每次提交命令携带：

- `gameId`
- `expectedVersion`
- `turnToken`
- `actorId`
- `idempotencyKey`

Event Store 采用乐观并发控制。重复提交相同 `idempotencyKey` 返回原结果；旧版本或旧 Turn Token 明确拒绝。

## 18. 领域错误分类

```text
RULE_VIOLATION
WRONG_PHASE
WRONG_ACTOR
STALE_GAME_VERSION
STALE_TURN_TOKEN
UNKNOWN_RULE_COMPONENT
INVALID_RULE_PACK
GAME_ALREADY_ENDED
```

领域错误不得包含 Provider 或 HTTP 概念。

## 19. 与 GameCoordinator 的边界

规则引擎只返回 NextRequirement 和 Domain Events。它不调用 Player Controller，也不等待模型或真人输入。

GameCoordinator 负责调度和收集；ActionCollector 负责持久化 Batch；RuleEngine 负责最终裁定。组队投票和任务行动必须按同一冻结状态逻辑并行收集。

完整规范见 [GameCoordinator 与动作收集规范](12-GameCoordinator与动作收集.md)。
