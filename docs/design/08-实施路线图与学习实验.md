# 08 - 实施路线图与学习实验

## 1. 实施原则

实现顺序必须从确定性内核走向非确定性边缘：

```text
Domain
-> Rule Packs
-> Application
-> Scripted/Human
-> Persistence
-> Harness
-> OpenAI Provider
-> Console/Web
-> Spring AI Adapter
-> Evaluation
```

不应先写 Prompt，再倒推游戏模型。

## 2. 阶段 M0：工程骨架

交付：

- Parent POM 和 Maven 模块。
- Java 21、Spring Boot 4.1.x 基线。
- 依赖边界说明。
- Bootstrap 启动模式。
- 配置目录约定。

验收：

- 所有模块依赖方向符合设计。
- Domain 模块不包含 Spring、Jackson、JPA 或 Provider 依赖。
- Bootstrap 是唯一可执行模块。

## 3. 阶段 M1：游戏领域内核

交付：

- Game 聚合。
- Command、Event 和 Action 类型。
- GameStatus、Phase、Turn Token。
- Player View 端口。
- 默认 Phase Handler 接口。

验收场景：

- 创建并开始一局空控制器的 5 人游戏。
- 角色分配由 seed 决定。
- 错误阶段动作被拒绝且不产生事件。
- 领域对象无需 Spring 容器即可运行。

## 4. 阶段 M2：规则包与经典 5 人局

交付：

- Rule Pack、Role、Setup YAML。
- Rule Pack Loader 和 Validator。
- 经典讨论、组队、投票、任务和刺杀阶段。
- 可见性投影。

验收场景：

- 5 人局任务人数和阈值正确。
- 好人无法提交失败任务票。
- 连续 5 次组队失败时邪恶获胜。
- 梅林、派西维尔、莫甘娜和刺客获得正确私有视图。

## 5. 阶段 M3：应用编排与 Scripted Player

交付：

- GameCoordinator 和 GameQueryService。
- NextRequirement 类型体系。
- ActionCollector、Single/Parallel Action Batch。
- PlayerController/Resolver。
- Scripted Player Controller。
- `advance` 和 `run` 用例。

验收场景：

- 一局 Scripted 5 人游戏可运行至结束。
- 同一 seed 和策略产生相同事件流。
- 应用层不重复计算任务结果和胜负。
- 组队投票和任务行动基于同一冻结状态逻辑并行收集。
- 收齐前任何玩家都看不到其他人的 Submission。

## 6. 阶段 M4：Human 等待态与 Console

交付：

- Human Player Controller。
- Pending Player Action。
- Console 命令和创建向导。
- 人工提交动作。

验收场景：

- LLM 尚未接入时即可运行 Human/Scripted 混合局。
- 等待 Human 时可以退出并恢复。
- 重复提交不会产生两次动作。

## 7. 阶段 M5：事件、快照与恢复

交付：

- Event Store 和 Snapshot Store。
- Action Batch Store 和 Action Submission Store。
- SQLite Adapter（本地默认）与 PostgreSQL Adapter（服务器部署）。
- Flyway Schema。
- Replay Projection。
- 配置冻结快照。

验收场景：

- 任意阶段重启后恢复相同状态。
- 回放不调用 Player Controller。
- 修改外部 Agent/Rule 配置不会影响运行中的游戏。
- 部分收集和已完成未提交的 Batch 均可在重启后恢复。

## 8. 阶段 M6：Harness 核心

交付：

- Agent/Harness Profile。
- Context Assembler。
- Skill Registry。
- Tool Registry 和 Tool Policy。
- Memory Policy。
- Budget、Validation、Retry 和 Failure Policy。
- Noop ModelClient 或固定响应 ModelClient。

验收场景：

- 固定模型响应可以走完整 Harness 并提交合法动作。
- 非法 Schema 触发一次修复。
- 越权 Tool 调用被拒绝。
- 预算耗尽后按 Failure Policy 暂停。

## 8.1 阶段 M6A：战略认知与社会博弈

这是进入真实 Provider 之前的强制里程碑，不得合并为一段通用 Prompt。

交付：

- `ObservationBatch` 和逐玩家观察游标。
- 公开发言、提案、逐人投票和任务结果的完整增量投影。
- Belief State、Evidence Assessment 和矛盾检测。
- Strategy State、Public Commitment、Cover Story 和 Deception Plan。
- 普通好人、梅林、派西维尔、莫甘娜、刺客和普通邪恶角色策略。
- Opening、Challenge、Response、Leader Summary 多轮讨论协议。
- 宿主确定性记忆写入与模型解释性记忆写入双通道。
- 战略场景评测和 `baseline-structured-v1` 对照 Harness。

验收场景：

- Agent 能引用真实可见事件解释判断。
- 他人公开发言不会被当作权威事实。
- 新证据可以驱动角色概率变化，并保留不确定性。
- 被质疑的 Agent 会回应具体问题而不是重复模板。
- 梅林能够引导但不会直接暴露私有知识。
- 邪恶角色能够维持公开伪装、选择性误导或切割队友。
- 任何欺骗都不能越过游戏信息权限和 Tool 权限。
- 战略 Harness 在固定场景中显著优于最小结构化基线。

完整规范见 [战略认知与社会博弈规范](10-战略认知与社会博弈.md)。

## 9. 阶段 M7：OpenAI Responses Provider

交付：

- Responses API HTTP Client。
- Typed Items 映射。
- Structured Outputs。
- Function Calling 循环。
- SSE Streaming。
- 错误、限流和 Usage 映射。
- 可选 `previous_response_id`。

验收场景：

- 真实模型可以完成讨论、投票、任务和刺杀动作。
- Provider 超时不会产生领域事件。
- Structured Output 和 Tool Calling 均可通过 Probe 检查。

## 10. 阶段 M8：完整 Console LLM 对局

交付：

- 模型、Agent、Harness 列表。
- 五个座位独立 Agent 绑定。
- 流式回合状态和成本显示。
- 暂停、重试、Human 接管。

验收场景：

- 五个不同配置 Agent 完成一局经典 5 人局。
- 一局中可以混用 LLM、Human 和 Scripted 玩家。
- 每个玩家上下文经审计不存在秘密泄漏。

## 11. 阶段 M9：REST 与 SSE

交付：

- Commands/Queries REST API。
- Public/Player/Admin SSE。
- 身份与权限边界。
- OpenAPI 文档。

验收场景：

- REST 与 Console 对同一命令产生一致领域事件。
- SSE 断线可以续传。
- 普通玩家不能读取管理员审计和其他玩家视图。

## 12. 阶段 M10：Spring AI 对照适配器

交付：

- Spring AI ModelClient。
- ToolCallback 映射。
- Advisor 和项目 Harness 的职责映射。
- Spring AI Observability 桥接。

验收场景：

- 相同 Agent Profile 可以切换原生 OpenAI 和 Spring AI Adapter。
- 切换不会改变领域、应用或 Player Controller 接口。
- 文档记录两个适配器的能力差异。

## 13. 阶段 M11：规则扩展

交付：

- 6 至 10 人标准 Setup。
- 不内置 11 人及以上非标准变体；未来若引入，必须作为独立 Rule Pack。
- 可选特殊角色。
- 可选额外阶段机制。

验收场景：

- 增加纯配置人数不修改主编排流程。
- 增加新阶段只注册新的 Phase Handler 和阶段图。
- 旧 Rule Pack 版本的回放不受新版本影响。

## 14. 阶段 M12：评测平台

交付：

- Tournament Runner。
- Seat/Role Rotation。
- Harness A/B 配置。
- JSONL 数据集导出。
- 成本、胜率、合法率和延迟报告。

验收场景：

- 同一模型比较不同 Harness。
- 同一 Harness 比较不同模型。
- 多 seed 结果可聚合且配置可追溯。

## 15. 第一个推荐可运行里程碑

第一个有价值的闭环不是“五个真实 LLM 自动玩完”，而是：

```text
经典 5 人规则
+ Scripted/Human 混合玩家
+ Event Store
+ 恢复与回放
+ Console
```

完成这个闭环后再接 LLM，可以准确判断问题属于游戏还是 Agent。

## 16. 第一个 Harness 学习里程碑

使用固定响应 ModelClient，比较：

- 一次性 Prompt。
- 分层 Context Block。
- Structured Outputs。
- Schema 加领域双重校验。
- 校验失败修复循环。

这个实验能直观看到 Harness 如何把模型不确定性变成受控执行。

## 17. 推荐学习实验

### 实验 A：同模型、不同 Prompt

验证 Prompt 文本对行为的影响，但保持 Harness 不变。

### 实验 B：同模型、不同 Harness

比较：

- 无 Memory 与结构化 Memory。
- 无 Tool 与投票分析 Tool。
- 全历史与预算化上下文。
- 无修复与有限修复。

### 实验 C：同 Harness、不同模型

观察能力声明、结构化输出合法率、成本和策略质量差异。

### 实验 D：Provider 状态模式

比较 `STATELESS_REPLAY` 和 `PREVIOUS_RESPONSE_ID` 的成本、延迟、恢复性与行为质量。

### 实验 E：真人混合

观察 Human 等待态如何证明 Console、REST、GUI 与 Controller 抽象是解耦的。

### 实验 F：规则扩展

从 5 人增加到 7 人，检查哪些变化只需要配置，哪些需要代码扩展点。

## 18. 旧项目迁移对照

| 旧项目概念 | 新项目处理 |
| --- | --- |
| `avalon-core` | 保留方向，进一步纯化为唯一领域真相 |
| `GameOrchestrator` | 拆为应用用例与领域 Phase Handler |
| `PromptBuilder` | 拆为 Context Assembler、Skill 和 Provider Renderer |
| `ResponseParser` | 拆为 Provider Mapper、Schema Decoder 和 Validator |
| `ValidationRetryPolicy` | 升级为分类 Validation/Retry/Failure Policy |
| `AgentGateway` | 升级为厂商无关 Model SPI |
| Chat Completions Gateway | 替换为 Responses Adapter |
| `PlayerMemoryState` | 升级为独立 Memory Policy 和 Store |
| Console Runner | 保留交互价值，只通过 Application API 工作 |
| REST API | 保留并增加 Human Action 与 SSE |

不建议复制旧代码后大规模重构。推荐按新模块边界逐步移植领域概念和配置资产。

## 19. 完成定义

项目整体完成至少满足：

- 五个不同 Agent 可完成默认 5 人局。
- 可混入真人玩家。
- 规则支持版本化并可扩展人数。
- OpenAI Responses 是默认协议，Provider SPI 可扩展。
- Spring AI 只作为可选适配器。
- 游戏可暂停、恢复和回放。
- Console 与 Web 共享应用核心。
- Agent 每回合具有完整 Trace、成本和校验记录。
- GameCoordinator 是唯一确定性推进服务，LLM 不参与规则裁定。
- 单人和多人动作都通过可恢复、幂等的 Action Batch 提交。
- 组队投票统一公开，秘密任务票永不公开来源。
- 评测可以比较模型、Prompt、Skill、Tool、Memory 和 Harness。
- Agent 能观察完整公开事件增量，维护证据化 Belief 和跨回合 Strategy。
- 讨论支持质疑、回应和队长总结，不是固定顺序独白。
- 角色策略、公开承诺和受控欺骗通过场景评测与基线对照验证。

## 20. 实施约束

- 每个里程碑保持可运行。
- 不提前创建微服务。
- 不在领域层引入框架注解。
- 不用 Prompt 修补领域模型缺失。
- 不把真实 Provider 调用作为唯一验证手段。
- 自动化测试的创建和运行必须遵守当前会话的用户授权策略。
