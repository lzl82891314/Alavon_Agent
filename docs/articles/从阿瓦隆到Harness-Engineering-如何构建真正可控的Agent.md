# 从阿瓦隆到 Harness Engineering：如何构建一个真正可控的 Agent

> 面向公司内部工程师、产品经理和对 Agent 感兴趣的同事
>
> 本文以一个多 Agent 阿瓦隆对战项目为例，解释 Harness Engineering 是什么、它解决了什么问题，以及为什么“给模型一段更长的 Prompt”远远不够。

## 摘要

很多 Agent Demo 看起来已经会聊天、会调用工具、会完成任务，但一旦进入真实环境，常见结果是：它们会按步骤输出总结，会重复模板，会把不该看到的信息混进上下文，也会把一段自然语言直接当成系统状态。模型似乎很忙，却没有真正的判断、记忆和策略。

阿瓦隆是观察这类问题的好实验场。游戏的核心不是发言数量，而是信息不对称：梅林知道部分邪恶阵营，邪恶玩家知道部分同伴，派西维尔只能看到模糊候选，忠臣几乎只能依靠公开行为推理。每个人都需要在有限信息下形成信念、影响别人、隐藏身份，并根据新证据修正判断。如果所有 Agent 都看到同一份全局状态，或者后投票的人能看到前面的票，游戏就不再是博弈，而是一个顺序执行的流程。

Harness Engineering 的价值，正是在模型之外建立一个可设计、可验证、可恢复、可审计的运行环境。它负责给每个 Agent 构造正确的观察空间，管理上下文和 Memory，限定工具与动作，校验模型输出，把不确定的推理与确定性的规则内核隔开，并通过评测确认系统是否真的产生了有意义的行为。

本文先从一个失败的阿瓦隆 Agent 讲起，再逐步抽象出 Harness 的概念，最后回到本项目的模块和实现，给出一套可以迁移到企业客服、研发助手、流程自动化和多 Agent 协作系统的工程方法。

## 一、为什么用阿瓦隆讲 Agent Engineering

阿瓦隆很适合做 Agent 工程的“显微镜”，原因有三点。

第一，游戏有明确的确定性规则。队伍是否合法、投票是否通过、任务是否成功、刺杀是否结束游戏，都应该由规则引擎决定，而不是由模型一句“任务成功”决定。这样可以清晰区分模型负责的部分和系统负责的部分。

第二，游戏天然存在权限边界。相同的事件，对不同玩家的可见性不同。梅林看到的内容不能直接交给忠臣，邪恶玩家的私密判断不能自动出现在其他玩家的 Memory 中。这正对应企业 Agent 中的租户隔离、文档权限和最小知识原则。

第三，游戏的质量不是“输出 JSON 就算成功”。一个合格的玩家需要回应质疑、引用证据、保持承诺一致、管理自己的公开叙事，必要时还要欺骗。也就是说，我们不仅要测协议合规，还要测跨回合行为和社会博弈能力。

因此，阿瓦隆同时覆盖了 Agent 系统最容易被忽略的四个问题：信息边界、状态管理、动作可靠性和行为评测。

## 二、阿瓦隆的核心不是发言，而是信息差

以经典角色为例：

| 角色 | 私有信息 | 公开目标 | 关键策略 |
| --- | --- | --- | --- |
| 梅林 | 能识别部分邪恶玩家，但不能暴露身份 | 帮助好人完成任务 | 通过含蓄建议影响队伍，避免被刺客识别 |
| 派西维尔 | 看到梅林和莫甘娜的候选身份，无法直接确认 | 保护梅林并帮助好人 | 保护正确候选，同时制造足够不确定性 |
| 莫甘娜 | 邪恶阵营知识，通常伪装成梅林候选 | 误导好人 | 利用“看起来像梅林”的行为争夺信任 |
| 刺客 | 邪恶阵营知识，终局可刺杀梅林 | 让任务失败并识别梅林 | 观察长期行为，在终局下注 |
| 莫德雷德 | 邪恶阵营身份，但可能不被梅林识别 | 隐藏在好人视野之外 | 降低明显邪恶信号，配合其他邪恶玩家 |
| 奥伯伦 | 邪恶身份，但不一定知道同伴 | 破坏好人协作 | 在信息不完整时独立行动 |
| 忠臣 | 没有私有阵营知识 | 依靠公开证据判断 | 识别矛盾、质疑过度自信的结论 |

如果所有玩家收到如下提示：

```text
当前所有玩家及其角色：A=Merlin, B=Assassin, C=Loyal Servant ...
请根据身份选择最优行动。
```

模型当然可以完成游戏，但这不是阿瓦隆。它只是在读取答案后执行规则。真正的游戏需要系统对每个玩家生成不同的 `PlayerTurnContext`，并且每个上下文只能包含该玩家有权知道的事实。

## 三、没有 Harness 时，Agent 为什么会退化成“流程总结工”

前身项目采用的是许多 Demo 常见的方式：拼接规则、历史记录和玩家身份，调用模型，让模型从自然语言中猜测下一步，然后直接修改游戏状态。这个方案短期内很容易跑通，但有几个结构性缺陷。

### 1. 全局状态直接进入 Prompt

开发者为了方便，把完整游戏对象序列化后传入每个 Agent。模型于是可能看到其他玩家的角色、私有记忆甚至管理员字段。即便 Prompt 写着“不要使用这些信息”，泄漏已经发生了。模型不是安全边界，禁止语句也不能替代权限控制。

### 2. 自然语言直接驱动领域状态

模型输出“我认为任务失败，所以任务失败”，或者输出一段 JSON，其中包含任意玩家、任意角色和任意阶段。若服务层只做浅层解析，模型实际上获得了修改领域状态的能力。结果可能是非法队伍、重复投票、越权查看信息，或者把自己的猜测写成世界事实。

### 3. 顺序执行暴露了本不该存在的信息

如果系统先调用 A 投票并把票写入状态，再调用 B，B 就能从状态里推断 A 的投票。阿瓦隆要求投票同时提交、之后统一揭示；顺序调用破坏了信息模型，即使每个 Prompt 都很优秀也无济于事。

### 4. 记忆等于“把全部历史再塞一次”

历史越长，Prompt 越长，模型越容易抓不住当前矛盾。没有结构化 Memory 时，模型无法区分“发生过的事件”“某人的公开说法”和“我自己的猜测”。它会把未经证实的判断当成事实，或者在新证据出现后仍机械复读旧结论。

### 5. 只测格式，不测博弈

只要输出包含 `action` 字段就判定成功，模型最容易学会的就是固定模板。它不需要回应别人，不需要引用证据，不需要维护叙事，更不需要承担欺骗的代价。

这些问题共同造成一种假象：Agent 每回合都在“思考”，实际上只是在完成一个没有状态边界、没有反馈闭环的表单。

## 四、Prompt Engineering 与 Harness Engineering 的区别

Prompt Engineering 主要回答“应该对模型说什么”；Harness Engineering 进一步回答“模型在什么环境里工作、能看到什么、能做什么、失败后怎么办”。两者不是互相替代，而是层级不同。

| 维度 | 只有 Prompt 的实现 | Harness Engineering 的实现 |
| --- | --- | --- |
| 指令 | 一段或几段文本 | 版本化的阶段指令、角色策略和动态上下文 |
| 上下文 | 尽量塞入完整历史 | 按权限投影、检索、压缩并记录来源 |
| 输出 | 依赖模型遵守格式 | Schema、解析器、领域校验和有限修复 |
| 错误 | 追加一句“请重试” | 分类、重试上限、修复提示、降级和暂停 |
| 能力 | Prompt 声称“你可以做某事” | Tool Registry 决定真正可调用的能力 |
| 记忆 | 原始对话无限增长 | 工作、情节、语义 Memory 分层并限额 |
| 安全 | 告诉模型不要泄密 | 服务端构造私有视图，未知事件默认私有 |
| 评测 | 看最终文本是否像样 | 看观察、信念、动作、成本、结果和轨迹 |

可以把 Agent 写成一个工程对象：

```text
Agent = Identity
      + Objective
      + Model Profile
      + Harness Profile
      + Skill Set
      + Tool Policy
      + Memory Policy
      + Budget Policy
      + Failure Policy
```

同一个模型可以被包装成不同的 Agent；更换模型也不应该迫使我们重写规则和权限层。

## 五、Harness 到底是什么

在本文语境中，Harness 是围绕模型的一套宿主系统。它把一次不确定的模型调用转换为一次受控的决策执行：

```text
读取权威状态
  -> 生成玩家观察投影
  -> 选择阶段能力、工具和 Memory
  -> 分配上下文预算
  -> 调用模型
  -> 解析结构化候选
  -> Schema 校验
  -> 领域预校验
  -> 有限修复或明确失败
  -> 返回 ProposedAction
  -> 由规则引擎提交并记录 Trace
```

它不是一个“更复杂的 Prompt 模板”，而是一个控制回路。模型只能提出候选动作，不能直接改变领域事实。规则引擎决定动作是否有效，协调器决定何时收集、何时提交，事件存储决定事实如何持久化，审计系统决定事后能否解释。

阿瓦隆项目中存在两层 Harness：

* `Game Harness`：阶段、规则、角色知识、动作 Schema、胜负判断、事件可见性和批次提交。
* `Agent Harness`：上下文、Skill、Tool、Memory、模型调用、预算、校验、重试、审计和 Trace。

两层通过 `PlayerTurnContext` 和 `ProposedAction` 交互。这个边界非常关键：Game Harness 不需要知道模型内部如何推理，Agent Harness 也不能绕过规则修改游戏状态。

## 六、一次 Agent 回合的完整生命周期

当前项目的 Agent 运行时可以拆成以下阶段。

### 1. Resolve Profile

宿主根据 `gameId + ownerPlayerId + agentInstanceId` 确定 Agent 身份、模型 Profile、Harness Profile、Skill 和预算。作用域由宿主创建，模型不能通过输出伪造另一个玩家的身份。

### 2. Build Observation

系统读取某个游戏版本的权威状态，并通过 `GameEventVisibilityPolicy` 投影出该玩家能看到的观察。公开事件和私有事件都带来源与可见性，未知事件默认按私有处理，避免新增事件时意外扩大权限。

### 3. Resolve Skills and Tools

讨论、组队、投票、任务选择、刺杀是不同阶段，不应把所有能力同时暴露。Skill 提供行为知识，Tool 提供确定性查询，例如查看公开时间线、统计投票记录、比较发言和投票的一致性。工具结果同样来自该玩家的可见数据投影。

### 4. Retrieve Memory

Agent 只检索自己的工作记忆、情节记忆和语义策略。Memory 更新是模型提出的建议，最终要经过 `MemoryPolicy` 过滤、归一化、证据绑定和容量限制。

### 5. Allocate Context Budget

上下文不是无限的。当前设计对观察、承诺、推断、世界事实、公开声明和摘要设置上限，送模的 `MemoryContextProjector` 默认约 12,000 字符，并优先保留当前信念、策略、沟通计划、近期承诺和最近事件。预算不足时先压缩低优先级内容，而不是让模型随机截断。

### 6. Execute Model Loop

模型可以生成公开发言、结构化动作、信念更新和策略更新草稿，但这些内容分别进入不同的后续路径。公开发言可以成为其他玩家的观察；私有认知草稿只能写入本 Agent 的 Memory；动作必须进入验证器。

### 7. Validate, Repair or Fail

先验证 JSON Schema，再验证领域约束。例如队伍成员必须存在、人数必须符合阶段、投票目标必须合法、证据引用必须属于当前 Agent 可见事件。失败时可以使用有限次修复调用；超过上限就返回明确失败，由协调器采取默认策略或暂停，而不是把半合法结果写进状态。

### 8. Commit and Trace

只有规则引擎接受 `ProposedAction` 后，领域事件才会提交。Trace 记录模型、参数、延迟、预算、校验结果、修复次数、决策摘要和证据引用，但不保存不必要的原始思维链。

## 七、信息边界：每个 Agent 必须拥有独立观察空间

### 1. 角色知识不是角色字段的复制

当前项目用角色知识矩阵描述“谁能看到什么”：

* `SEE_PLAYERS_BY_CAMP`：只能看到目标玩家的阵营。
* `SEE_ALLIED_EVIL_PLAYERS`：知道部分邪恶同伴，但不一定知道精确角色。
* `SEE_PLAYERS_BY_ROLE`：只有规则明确时才能看到精确角色。
* `SEE_ROLE_AMBIGUITY`：看到候选角色集合，但不携带真实阵营。

这解决了几个典型漏洞：梅林不能因为看到邪恶阵营就知道谁是刺客或莫甘娜；邪恶玩家不能自动看到所有同伴的精确角色；派西维尔的梅林/莫甘娜候选不再通过真实 `camp` 字段泄漏答案。

### 2. 不能依赖 Prompt 保密

正确的做法是服务端先构造数据，再把数据传给模型：

```java
PlayerTurnContext context = contextFactory.forPlayer(state, playerId);
// context contains only playerId-authorized facts
AgentExecutionResult result = controller.execute(context);
```

模型即使请求“查看其他玩家 Memory”，工具层也必须拒绝。普通游戏服务不暴露管理员审计和私有视图；管理员查询迁移到带 `AdminInspectionCapability` 的专用服务。

### 3. 冻结批次同样是信息边界

投票和任务选择采用统一批次：

```text
从同一游戏版本生成所有 PlayerTurnContext
  -> 并行/顺序调用 Controller，但上下文保持冻结
  -> 收齐 ProposedAction
  -> 校验完整批次
  -> 一次性提交
  -> 揭示汇总结果
```

因此后投票 Agent 看不到前票。这里的“冻结”不是并发优化，而是游戏规则的一部分。

## 八、三层事实模型：WORLD_FACT、PUBLIC_CLAIM、PRIVATE_BELIEF

多 Agent 系统最容易犯的错误，是把模型说过的话直接升级为事实。当前设计把信息分为三层。

`WORLD_FACT` 是规则引擎确认的事实，例如某轮任务成功、某个队伍被提交、某玩家投了赞成票。它只能由确定性内核产生。

`PUBLIC_CLAIM` 是玩家公开说过的话，例如“我认为 C 很可疑”。它属于公共事件，其他玩家可以观察、引用和质疑，但不等于真实身份。

`PRIVATE_BELIEF` 是某个 Agent 的主观信念，例如“C 是邪恶的概率 0.7”。它只能存在于该 Agent 的私有 Memory 中，必须有证据引用和变更幅度约束。

数据流应当是：

```text
规则内核 -> WORLD_FACT -> 各玩家观察投影
玩家发言 -> PUBLIC_CLAIM -> 其他玩家各自解释
玩家推理 -> PRIVATE_BELIEF -> 本人 Memory
```

不能反过来把 `PUBLIC_CLAIM` 自动写成 `WORLD_FACT`，也不能把一个 Agent 的 `PRIVATE_BELIEF` 广播给所有人。

## 九、Memory：不是把历史全部塞进 Prompt

一个可用的 Agent Memory 至少应分层：

* Working Memory：本次回合推理所需的临时上下文。
* Episodic Memory：本局关键事件、承诺、怀疑变化和对话节点。
* Semantic Memory：稳定的角色策略、沟通偏好和长期规则知识。
* Provider Context：模型供应商保存的响应链，可作为缓存，但不是权威游戏状态。

模型可以提出 Memory 更新，但宿主会检查：目标玩家是否存在，概率是否在 `[0,1]`，无证据时变化是否过大，证据是否属于当前可见事件，私有已知阵营是否保持一致。当前实现还支持按玩家绑定 `beliefEvidenceReferences`，避免一条全局证据被同时用来支持多个不相关的信念变化。

Memory 预算的意义不只是节省费用。它迫使系统明确“哪些信息值得被记住”，也使每次决策可重放：我们能够知道当时保留了哪些观察、压缩了哪些旧记录、使用了多少字符预算。

需要注意，当前预算主要按字符估算，并非 Provider tokenizer 的精确 Token；这属于工程近似，不能拿来做精确计费结论。

## 十、让角色真正参与博弈，而不是只贴一个身份标签

把 `role=Merlin` 写进 System Prompt 不等于实现了梅林。角色策略必须同时存在于目标、可见信息、Memory、公开承诺和评测中。

### 梅林

梅林的目标不是“直接指出所有邪恶玩家”，而是在不暴露自己的前提下影响队伍。Harness 可以允许它在私有认知中使用阵营事实，却要求公开发言引用公共证据或模糊表达，并在刺杀阶段评估其长期行为是否过于精准。

### 派西维尔

它应当维护“梅林/莫甘娜候选”而不是一个带真实阵营的答案。若候选结构中含有 `camp`，模型就能绕过游戏不确定性。

### 邪恶阵营

邪恶玩家不应无脑抱团。莫甘娜可以争夺梅林候选，莫德雷德可以降低可见性，奥伯伦可以在缺少同伴知识时独立制造噪声，刺客则需要把全局行为转化为终局判断。Harness 的职责是提供不同的知识和行动空间，并要求模型产生 `deceptionPlan`、`coverStory` 或目标受众等结构化意图；这能让行为可观察、可评测，但不保证欺骗一定有效。

### 忠臣

忠臣需要根据公开证据形成独立判断，不能因为多数人重复某句话就自动提高置信度。没有证据时的信念变化幅度限制，是抵抗从众和幻觉的基础。

## 十一、讨论协议：从固定独白到社会互动

真正的讨论不是每个人轮流说一段“我认为某某可疑”。当前设计把讨论拆成 Opening、Challenge、Response、Synthesis 等阶段。

* Opening：陈述当前判断和队伍建议。
* Challenge：针对具体玩家、队伍或承诺提出质疑。
* Response：被点名玩家必须回答具体问题，并引用可见证据。
* Synthesis：队长或当前发言者总结分歧、风险和下一步动作。

结构化输出可包含 `targetPlayerId`、`challengePoint`、`evidenceRefs`、`publicClaim` 和 `desiredAudienceBelief`。这样既保留自然语言，也让系统能统计“是否回应了问题”“是否引用了与目标玩家绑定的证据”“是否只是重复通用模板”。

注意，协议门槛只是最低要求。一个 Agent 可以非常合规地说废话，所以项目又增加了战略门槛，例如至少发生一次有证据支持的信念修正、在邪恶角色出现时产生欺骗计划、维持公开叙事的一致性。它们仍是行为代理指标，而不是策略正确性证明。

## 十二、结构化输出：模型只能提出动作

推荐的结果结构大致如下：

```json
{
  "publicSpeech": {
    "kind": "CHALLENGE",
    "targetPlayerId": "P3",
    "text": "你上一轮反对包含 P1 的队伍，但这次又支持相同组合，原因是什么？",
    "evidenceRefs": ["event-42"]
  },
  "proposedAction": {
    "type": "TEAM_VOTE",
    "value": "REJECT"
  },
  "beliefUpdate": {
    "playerId": "P3",
    "probabilityEvil": 0.65,
    "evidenceRefs": ["event-42"]
  },
  "strategyUpdate": {
    "deceptionPlan": null,
    "coverStory": "我坚持以投票与任务结果的一致性作为主要依据"
  }
}
```

模型只是提出这个对象。Schema 验证字段类型，领域预校验检查动作合法性，规则引擎最终决定是否产生领域事件。若队伍人数错误，系统拒绝该动作；若信念变化没有证据，系统拒绝 Memory 更新但仍可以保留合法投票；不同产物可以分别成功或失败。

这就是“确定性内核 + 非确定性边缘”：模型负责解释、推理和策略，代码负责权限、状态、规则和提交。

## 十三、Validation、Retry、Coordinator：把失败变成可管理的状态

模型失败不是单一类型。至少要区分：Provider 超时、输出截断、JSON 解析失败、Schema 失败、领域动作非法、证据越权、Memory 更新越界和批次冲突。

每类失败都应有明确策略：

* 可修复的格式错误：带校验反馈进行一次或少量修复调用。
* 不可修复的动作错误：放弃该候选，使用配置的默认策略或标记 Agent 失败。
* Provider 不可用：切换备用模型或进入暂停状态。
* 批次冲突：重新基于同一版本生成，而不是接受部分提交。

`GameCoordinator` 负责收集动作、冻结上下文和推进阶段；`GameOrchestrator` 负责恢复、重放和运行到结束。Controller 不应该自己推进游戏，否则每个 Agent 都可能以不同方式解释阶段边界。

## 十四、安全、审计与可观测性

安全不是在 Prompt 末尾加一句“不要泄密”。需要记录并能够回答：

* 本次模型看到了哪些事件和 Memory 条目？
* 这些内容的可见性来源是什么？
* 模型提出了什么动作和信念变化？
* 哪些字段被校验器拒绝或修复？
* 最终由规则引擎提交了哪些事件？

审计记录决策目标、简短理由摘要、公开证据引用、置信度、最终动作、模型与参数、延迟和 Token/字符预算，不要求保存完整 Chain of Thought。管理员可以通过 capability-gated 的 `AdminGameInspectionService` 查看全局回放和私有视图，但普通玩家服务不暴露这些入口。未来增加 HTTP Controller 时，不能让客户端自行构造管理员 Capability。

## 十五、如何评测“有博弈”

评测应分三层。

### 协议层

检查是否按阶段发言、是否回应质疑、是否提交合法动作、是否产生非法事件。当前代码已有协议门槛和结构化审计统计，仓库记录的 23 项回归检查全部通过，但这并不等于本轮重新执行了 Maven 测试；当前环境没有可用 Java/Maven。

### 战略行为层

固定场景应覆盖：矛盾识别、抵抗从众、证据修正、梅林隐藏、莫甘娜伪装、邪恶切割、刺杀判断、承诺一致、证据不足时保持不确定。`StrategicBehaviorEvaluator` 已将协议门槛与战略门槛分开，并要求最低信念修正、证据支持、邪恶角色的欺骗计划和叙事一致性。

但这些指标有边界：一次信念修改即可满足最低条件，`deceptionPlanCount > 0` 只说明字段存在，不能证明欺骗有效；没有既有 Cover Story 的短样本，其一致性评分也可能偏宽松。还没有完整的矛盾检测工具、两阶段推理和策略正确性证明。

### 真实模型对照层

需要在相同角色、座位、随机种子和场景下比较：

```text
baseline：最小 Prompt + 结构化动作
strategic Harness：完整上下文、Memory、角色策略和评测门槛
```

至少使用多个模型、多个 seed 和多轮局数，观察证据引用率、模板重复率、矛盾识别率、角色专属行为、首轮合法动作率、平均成本和延迟。当前项目尚未配置真实 Provider/API Key，不能宣称已经证明真实模型稳定具备高水平博弈能力。

## 十六、有 Harness 与没有 Harness 的对比

| 场景 | 没有 Harness | 有 Harness |
| --- | --- | --- |
| 信息 | 所有 Agent 可能拿到同一份全局对象 | 按玩家、角色和事件策略生成观察投影 |
| 私有记忆 | 共享或通过 Prompt 间接泄漏 | 每个 Agent 独立存储、独立投影 |
| 投票 | 顺序写入，后者看到前票 | 冻结上下文，收齐后统一揭示 |
| 发言 | 固定轮流独白 | Opening/Challenge/Response/Synthesis |
| 判断 | 模型直接修改状态 | 模型提出动作，规则引擎提交事实 |
| 记忆 | 无限追加原始历史 | 分层、限额、压缩、证据绑定 |
| 错误 | 追加“请重试” | 分类、有限重试、修复、降级、暂停 |
| 审计 | 只能看最终文本 | 可追踪观察、来源、校验、提交和成本 |
| 评测 | JSON 合法即通过 | 协议、战略结构和真实对照分层评测 |

Harness 并不会凭空创造更强的模型，但它防止系统在观察、记忆、交互和状态层面先把模型能力上限压垮。没有泄漏的信息差、可持续的 Memory 和对质询的响应机会，模型再大也只能做流程填空；有了这些宿主条件，模型的推理能力才有可能转化为可观察的策略行为。

## 十七、从阿瓦隆迁移到企业 Agent

### 1. 客服 Agent

客户资料、订单信息、内部政策和其他客户对话应当拥有不同可见性。模型只能提出退款或升级建议，真正的退款由权限和规则服务执行。公开回复、内部判断和审计摘要必须分层保存。

### 2. 研发助手

代码、Issue、CI 结果和生产凭据不是同一种事实。Agent 可以根据可见日志提出修复补丁，但不能直接把猜测写成事故结论，也不能读取无关项目的私有仓库。补丁需要编译、测试和安全扫描后才能合并。

### 3. 流程自动化

审批 Agent 需要知道当前步骤、审批人和可执行动作；它不应看到所有历史审批人的私密意见。顺序审批中的“冻结快照、统一提交”与阿瓦隆的同时投票完全同构。

### 4. 多 Agent 协作

每个 Agent 都应有明确的身份、目标、能力、记忆和权限。共享消息是公共声明，不是共享内心；协调器负责收集和提交，不能让一个 Agent 通过工具绕开另一个 Agent 的授权边界。

## 十八、常见误区

**误区一：Harness 就是更长的 System Prompt。** 长文本不能提供真正的权限、事务和恢复能力。

**误区二：结构化 JSON 等于可靠。** JSON 只解决可解析性，仍需 Schema 和领域校验。

**误区三：把所有历史都保留就是有记忆。** 没有优先级和来源的历史会降低判断质量。

**误区四：要求模型解释完整思维链才能审计。** 审计应记录可验证的输入、证据、摘要和动作，不应把不可控的内部推理当作产品契约。

**误区五：出现 deception 字段就代表会欺骗。** 字段存在只是可观察性，必须用对照实验检验欺骗是否影响受众信念并符合角色目标。

**误区六：回归测试通过就代表 Agent 聪明。** 回归测试主要证明宿主约束没有被破坏；真实智能还需要 Provider、多 seed、多角色、多局面的实验。

## 十九、分阶段落地路线

如果从零构建一个企业 Agent，可以按以下顺序推进：

1. 先定义确定性内核：状态、规则、权限和不可变事件。
2. 为每个用户或 Agent 构造独立观察投影，未知信息默认拒绝。
3. 用 Schema 约束动作，让模型只能提出候选而不能修改事实。
4. 引入有限重试、失败分类、超时和降级策略。
5. 将 Memory 分成工作、情节、语义层，添加容量、来源和变更约束。
6. 把互动协议结构化，要求质询、回应、总结和证据引用。
7. 建立 Trace、审计和回放，确保每次决策可解释、可复现。
8. 先做固定场景评测，再做真实 Provider 的多模型、多 seed A/B 对照。
9. 最后才根据数据调整 Prompt、模型和策略参数。

这个顺序的核心是先让系统可控，再让行为变聪明。否则你无法判断一次失败究竟来自模型能力、上下文缺失、信息泄漏、规则错误还是重试策略。

## 二十、结语：Harness 不是限制模型，而是保护模型的上限

阿瓦隆项目给出的最重要启示是：Agent 的智能不是孤立存在于模型回答里的。它取决于模型看到什么、记住什么、能调用什么、如何面对反馈，以及系统是否允许它把一次猜测逐步变成可靠行动。

没有 Harness，系统会把权限、状态、上下文和失败处理全部交给自然语言，最终得到一个看似能说话、实际上只会打卡的流程机器人。有 Harness，模型被放进一个信息边界清晰、动作受控、反馈闭环完整的环境，才有机会表现出信念更新、社会推理、欺骗和长期策略。

因此，Harness Engineering 的目标不是把 Agent 变成一个被规则锁死的脚本，而是把确定的部分交给确定性系统，把不确定但有价值的部分留给模型，并让两者之间的边界足够清楚。阿瓦隆只是一个小型实验场；同样的思想可以成为企业级 Agent 的基础工程方法。
